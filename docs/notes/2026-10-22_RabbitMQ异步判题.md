# 2026-10-22 RabbitMQ 异步判题

> 记录把「提交后线程池异步调 Feign」改成「发 MQ + judge 消费」的落地过程。
> 原理与教程见 vault 笔记《RabbitMQ 实战：从概念到 OJ 异步判题》。

## 1. 改造前后

| | 改造前 | 改造后 |
|---|---|---|
| 触发 | `CompletableFuture.runAsync(() -> judgeFeignClient.doJudge(id))` | `rabbitTemplate.convertAndSend(...)` |
| 可靠性 | 重启丢在途任务 | 消息在队列里，重启后继续消费 |
| 削峰 | 无 | 队列缓冲，消费者按能力取 |
| 耦合 | 提交接口依赖判题服务地址 | 只依赖 exchange/routingKey |

## 2. 拓扑

```
haxoj.judge.exchange (direct)
  └─ judge.submit ──▶ haxoj.judge.queue (durable)
                          │ x-dead-letter-exchange: haxoj.judge.dlx
                          │ x-dead-letter-routing-key: judge.dlq
                          ▼
                     haxoj.judge.dlx ──▶ haxoj.judge.dlq
```

消息体：`JudgeMessage { questionSubmitId, timestamp }`（只带 id，消费方回查）。

## 4. 关键决策

1. **消息只带 id**：小、不过期、消费时拿最新数据。
2. **手动 ack**：成功 / 业务失败 / 系统失败三态分开。
   - 业务异常 → ack（重试无意义，防毒消息）；
   - 系统异常 → 重置 WAITING + `nack(requeue=false)` → DLQ。
3. **不用 `requeue=true`**：会死循环打满 CPU。
4. **幂等**：状态检查 + `UPDATE ... WHERE status=WAITING` 原子抢占。
5. **发送确认**：`publisher-confirm-type: correlated` + `publisher-returns`，失败有日志。

## 5. 实测结果（2026-10-22）

- 队列：`haxoj.judge.queue`（0 条，1 消费者）、`haxoj.judge.dlq`（1 条，故障演练留下）。
- 提交后状态：`0 WAITING → 1 RUNNING → 3 FAILED`。
- `judgeInfo`：`{"message":"Wrong Answer","memory":0,"time":0}`。
  （测试代码是回显，判题逻辑正常。）
- 故障演练：停沙箱 → 消费者捕获异常 → 重置 WAITING → 消息进 DLQ。

## 6. 踩坑记录

| 现象 | 原因 | 解决 |
|---|---|---|
| TCP 通但 AMQP 握手超时 | Docker `-p` 的 proxy 转发不到容器 | 容器改用 `--network host` |
| 沙箱 `/sandbox/execute` 404 | VM 上是旧 jar | 在 VM 上 `mvn package` 重启 |
| 提交卡在 RUNNING | 沙箱失败被包成 `BusinessException`，消费者误 ack | 改抛 `RuntimeException` → 走 DLQ + 重置 |
| 管理台/CLI 卡住 | 该 VM 的 Erlang 分布式解析问题 | 优先用管理台 15672；CLI 仅辅助 |
