# 2026-10-27 判题正确性与幂等修复

> 一次提交到出结果这条链路上，有三处会给出**与事实不符的结论**：选了不支持的语言被判成平台故障、
> Java 超时几乎永远判不出来、通过数会重复累加。这次一起修掉，顺带堵住「提交永久卡在判题中」的异常分支。
> 判题策略的原理见 [`2026-09-17_判题功能全景解析.md`](./2026-09-17_判题功能全景解析.md)，
> MQ 拓扑见 [`2026-10-22_RabbitMQ异步判题.md`](./2026-10-22_RabbitMQ异步判题.md)。

## 1. 修了什么

| # | 现象 | 用户看到的结果 | 根因 |
|---|---|---|---|
| 1 | 选 C++ / Go 提交 | 「系统错误」 | 沙箱只认 java，返回 `status=2`（平台故障语义），判题侧据此定性 |
| 2 | 死循环程序 | 「成功」或「答案错误」，永远不超时 | `(time - 10000) > timeLimit`，而沙箱执行上限只有 5 秒 |
| 3 | 同一条提交被重放 | 题目通过数多加一次 | 状态回写与 `acceptedNum+1` 是两次远程调用，重试不幂等 |
| 4 | 抢占成功后抛业务异常 | 永远「判题中」 | 消费者对业务异常只 ack，不落定状态 |

## 2. 语言口径：只保留 Java

- 前端做题页的 `languageOptions` 只留 Java（`ProblemDetail.vue`）。下拉、Monaco 语言映射、切换语言时替换骨架的结构全部保留，将来加语言不用重写。
- 后端在提交入口加显式拦截：枚举校验通过但语言不是 Java → `PARAMS_ERROR`「当前仅支持 Java 提交」。
- **不删枚举值**：一是历史数据里可能有 c++ / golang 记录，二是接新语言时枚举不用来回改。
- **沙箱不动**：它返回 `status=2` 的协议保持原样。提交入口已经拦住，这条路径不可达；改协议要两端同时上线，收益不成比例。

> 关键判断：让用户看到「暂不支持」比看到「系统错误」重要。
> 前者他会换语言，后者他会等平台恢复 —— 等一个永远不会来的修复。

## 3. 时间与内存判定

### 3.1 判定顺序改了

```
内存 → 时间 → 输出条数 → 逐项内容
```

原来先比输出，被超时掐断或被 OOM 杀掉的程序输出不完整，会先命中「条数不等」→ 判成「答案错误」。
用户拿着「答案错误」去改算法，而实际该做的是降复杂度。**资源超限是更接近事实的结论。**

### 3.2 时间宽限

| 策略 | 宽限 | 判定式 |
|---|---|---|
| `DefaultJudgeStrategy` | 0 | `time > timeLimit` |
| `JavaLanguageJudgeStrategy` | 1000ms | `time > timeLimit + 1000` |

宽限只应该覆盖「算法还没开始跑」的固定开销（JVM 启动、docker exec）。
1000ms 是实测 openjdk:8-alpine 冷启动（约 100~300ms）留出的余量，不是给慢算法开后门。

> 原来那个 10 秒常量必须小于沙箱的 5 秒上限才有意义 —— 这是这次最容易看漏的一点：
> 宽限大于执行上限，等于把「超时」这个结论从词典里删掉。

### 3.3 空值语义统一为「未设置限制即不判」

| 情况 | 处理 |
|---|---|
| `judgeConfig` 为空 / 解析失败 | 跳过资源判定，只比输出（记 DEBUG，不刷 WARN） |
| `memoryLimit` / `timeLimit` 为 null | 跳过该项 |
| 沙箱没采到 `time` / `memory` | 按 0 参与比较 |
| 预期输出为 null | `Objects.equals(expected, actual)`，不 NPE |
| 题目没有测试用例 | 判 `System Error`，**绝不**因为「0 == 0」放行成 Accepted |

最后一条是顺带发现的：用例数为 0 时原来会判成「成功」，任何代码都能过。这比判错更糟。

## 4. 幂等：单事务 finish

### 4.1 契约

```java
// QuestionFeignClient
@PostMapping("/question_submit/finish")
boolean finishQuestionSubmit(@RequestBody QuestionSubmitFinishRequest request);
```

请求体只带 `id` / `status`（2 成功、3 失败）/ `judgeInfo`。
**刻意不含 questionId**：通过数加给哪道题，由 question-service 自己按提交记录查，
调用方传什么就加什么的话，传错一个 id 就把别人的通过数加上去了。

返回值只回答一件事 —— **要不要重试**：

| 返回 | 含义 | 调用方动作 |
|---|---|---|
| `true` | 提交现在已是终态（本次落定成功，或此前已落定，幂等命中） | ack |
| `false` | 状态既非「判题中」也非终态（记录不存在 / 仍是 WAITING） | 抛系统异常，走 DLQ |

### 4.2 提供方实现（question-service）

```
① 按 id 读记录 → 拿 questionId 与当前 status（不信任调用方）
② 已是终态 → 直接 return true
③ 条件更新 WHERE id=? AND status=RUNNING（0 行则回读区分幂等与异常）
④ 本次落到 SUCCEED 才 acceptedNum = acceptedNum + 1
⑤ ④ 失败 → 抛异常整笔回滚
```

第 ③ 步的 `WHERE status=RUNNING` 就是幂等闸门：MySQL 驱动默认返回「匹配行数」，
第二次执行时状态已经不是 RUNNING，稳定返回 0 行。
第 ④ 步只在「本次真的推进了状态」时执行，幂等命中的分支在第 ② 步就返回了。

### 4.3 为什么用 `update(wrapper)` 而不是 `updateById`

`updateById` 按主键更新，没有状态守卫；`update(wrapper)` 才能表达
「只有还在判题中，才允许落定」这个前提。状态机的守卫要写在 SQL 里，不能写在 Java 的 if 里 ——
Java 里的检查和更新之间永远有窗口。

## 5. 异常分支收口

| 情况 | 处理 |
|---|---|
| 成功 | ack |
| 业务异常（提交不存在、题目不存在、状态不允许） | 先尽力 `finish(FAILED, System Error)`，再 ack |
| 系统异常（沙箱挂了、网络） | 重置 WAITING + `nack(requeue=false)` → DLQ |

业务异常仍然 ack（重试无意义，不能变毒消息），但**不再只是 ack**：
异常可能发生在抢占成功之后，此时提交已是 RUNNING，消息一 ack 就再没人管它，前端永远转圈。
落定用的是带 `WHERE status=RUNNING` 守卫的 finish，所以不会把一条已成功的提交改坏。

## 8. 遗留

- [ ] Docker 容器内存上限写死 100MB，而题目默认 memoryLimit 是 256MB —— 正常解也可能被判内存溢出。应让容器上限跟着题目的 memoryLimit 走。
- [ ] `submitNum + 1` 仍是 `synchronized(this)` + 读改写，多实例下会丢更新；应改为 `setSql("submitNum = submitNum + 1")`。
- [ ] DLQ 里的消息没有重放工具，只能人工处理。
- [ ] 沙箱对「运行错误」和「编译错误」都返回 `status=3`，判题侧只能统一归为编译错误 —— 要精确区分得扩协议。
- [ ] 业务异常落定后消息直接 ack，用户看到的是「系统错误」而不是具体原因；要透出原因得扩 `judgeInfo` 的语义。
