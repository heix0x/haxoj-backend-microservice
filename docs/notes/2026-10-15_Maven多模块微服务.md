# Maven 多模块组织微服务改造笔记

> 项目：在线判题系统 `haxoj`，模块目录 `haxoj-backend-microservice`。
> 本笔记记录把「一堆各自为政的 Maven 工程」整理成「一个父工程 + 若干子模块」的完整过程，包含改造前后的真实差异、每一步的配置要点、实际踩过的坑，以及可直接落到下一个微服务项目里的通用规范。

---

## 一、改造前 vs 改造后

### 1.1 改造前的真实状态

`haxoj-backend-microservice` 目录下其实已经躺了 7 个模块的代码，但只有 `common`、`model` 两个被父工程 `<modules>` 聚合，其它 5 个（`service-client`、`gateway`、`user-service`、`question-service`、`judge-service`）是**没爹的独立工程**：

```
haxoj-backend-microservice/           ← 父工程，packaging=pom，但只聚合了 common/model
├── haxoj-backend-common/             ← 有 parent
├── haxoj-backend-model/              ← 有 parent
├── haxoj-backend-service-client/     ← 无 parent，自己写 groupId/version/BOM/插件
├── haxoj-backend-gateway/            ← 无 parent，同上
├── haxoj-backend-user-service/       ← 无 parent，同上
├── haxoj-backend-question-service/   ← 无 parent，同上
└── haxoj-backend-judge-service/      ← 无 parent，同上
```

### 1.2 改造前暴露出的具体问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 5 个模块没有 `<parent>`，各自独立声明 `groupId`/`version`/`properties` | 同名依赖可能出现 5 个版本，升级要改 5 处 |
| 2 | 每个模块都复制了一遍 `spring-boot-dependencies`、`spring-cloud-dependencies` 两个 BOM 的 `<dependencyManagement>` | 重复配置，且 `service-client` 里 `spring-cloud.version=2021.0.5`、父工程 `spring-cloud-alibaba.version=2021.0.5.0`，两套版本源 |
| 3 | 父工程把 `spring-cloud-dependencies` 写在 `<dependencies>` 里并带 `scope=import` | 位置错误：BOM 属于 `dependencyManagement`，放 `<dependencies>` 不生效还误导人 |
| 4 | 父工程 `<dependencies>` 塞了 `spring-boot-starter-web`、`nacos-discovery`、`sentinel`、`mybatis-plus`、`mysql`、`devtools` | 一旦子模块挂上父工程，连网关和公共库都会被迫继承 Web/MyBatis；**网关继承 `spring-boot-starter-web` 会与 Gateway 的 WebFlux 直接冲突** |
| 5 | `common`/`model` 把编译级别设成 `11`，父工程与其它模块是 `1.8` | 同一个工程两种字节码级别，跨模块引用时容易出现 `Unsupported class file major version` |
| 6 | 每个模块都复制了 `maven-compiler-plugin` + `spring-boot-maven-plugin` 的完整配置 | 重复且版本不一致 |
| 7 | 父工程给 `spring-boot-maven-plugin` 写死了一个**并不存在**的 `mainClass` 且 `skip=true` | 所有服务都打不出可执行包（实测：第一次构建产出的 jar 只有 10KB） |
| 8 | 同时引了 `mybatis-spring-boot-starter` 与 `mybatis-plus-boot-starter` | 功能重叠，MyBatis-Plus starter 已包含 mybatis-spring |

### 1.3 改造后的目标结构

```
haxoj-backend-microservice/                     ← 父工程（打包类型 pom）
├── pom.xml                                     ← 聚合 + 版本/插件集中管控
├── haxoj-backend-common/                        ← 公共库（不引 Web）
├── haxoj-backend-model/                         ← 领域模型库
├── haxoj-backend-service-client/                ← 服务间调用客户端库
├── haxoj-backend-gateway/                       ← 可执行服务（WebFlux）
├── haxoj-backend-user-service/                  ← 可执行服务
├── haxoj-backend-question-service/              ← 可执行服务
└── haxoj-backend-judge-service/                 ← 可执行服务
```

改造后 8 个模块一次 `mvn package` 全绿，4 个可执行服务各产出一个 46–66MB 的 fat jar，3 个公共库仍然是几十 KB 的普通 jar。

## 二、先分清两个容易混的机制：聚合 与 继承

这是多模块项目最容易搞错的地方，二者**互相独立、可以只用一个**：

| 机制 | 写在哪 | 作用 | 本项目用法 |
|---|---|---|---|
| **聚合** (aggregation) | 父工程 `<modules>` | 一次命令构建多个模块，Maven 按依赖关系自动排出构建顺序 | 父工程列全部 7 个子模块 |
| **继承** (inheritance) | 子模块 `<parent>` | 子模块继承父工程的 `properties` / `dependencies` / `dependencyManagement` / `pluginManagement` | 每个子模块指向父工程 |

要点：

- **聚合不等于继承**。父工程 `<modules>` 里列了 A，只是说“构建时带上 A”，A 并不会自动获得父工程的配置，除非 A 自己写了 `<parent>`。
- **继承也不等于聚合**。子模块写了 `<parent>`，就算父工程没聚合它，它照样能继承；但只有被聚合才能“一条命令全量构建”。
- 父工程自己**必须**是 `<packaging>pom</packaging>`，否则不能被继承。

> 所以最省心的写法是**两个都配**：父工程列全所有 `<modules>`，每个子模块第一段就写 `<parent>`。本项目最终就是这样。

本项目实际的 reactor 构建顺序（Maven 通过模块间依赖自动推导，不用手排）：

```
haxoj-backend-microservice (pom)
  → haxoj-backend-common
  → haxoj-backend-model
  → haxoj-backend-service-client
  → haxoj-backend-gateway / user-service / question-service / judge-service（可并行）
```

## 三、父工程 pom.xml 逐段讲解

父工程只做三件事：**聚合、管版本、管插件**。它不写业务依赖的实现细节。

### ① `<modules>`：一处声明，全量构建

```xml
<modules>
    <module>haxoj-backend-common</module>
    <module>haxoj-backend-model</module>
    <module>haxoj-backend-service-client</module>
    <module>haxoj-backend-gateway</module>
    <module>haxoj-backend-user-service</module>
    <module>haxoj-backend-question-service</module>
    <module>haxoj-backend-judge-service</module>
</modules>
```

注意子模块目录名要和 `<module>` 值一致；新增模块时**这里必须补一行**，否则 `mvn package` 会默默跳过它（这是最隐蔽的坑之一）。

### ② `<properties>`：版本号唯一来源

```xml
<properties>
    <java.version>1.8</java.version>
    <maven.compiler.source>${java.version}</maven.compiler.source>
    <maven.compiler.target>${java.version}</maven.compiler.target>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <project.reporting.outputEncoding>UTF-8</project.reporting.outputEncoding>

    <spring-boot.version>2.6.13</spring-boot.version>
    <spring-cloud.version>2021.0.5</spring-cloud.version>
    <spring-cloud-alibaba.version>2021.0.5.0</spring-cloud-alibaba.version>

    <gson.version>2.9.1</gson.version>
    <easyexcel.version>3.1.1</easyexcel.version>
    <hutool.version>5.8.8</hutool.version>
    <commons-collections4.version>4.4</commons-collections4.version>
    <mybatis-plus.version>3.5.2</mybatis-plus.version>
</properties>
```

- `maven.compiler.source/target` 直接引用 `${java.version}`，这样 IDE 与 Maven 用的是同一个编译级别，杜绝本项目改造前 `common/model` 是 11、其它是 1.8 的错位。
- 版本号**一律**用 `<属性>` 承接，绝不把 `2.9.1` 这种字面量写在 `<dependency>` 里——否则升级时要全工程搜字符串。

### ③ `<dependencyManagement>`：只管“要哪版”，不管“要不要”

```xml
<dependencyManagement>
    <dependencies>
        <!-- 3.1 非 Spring 生态：显式版本，必须写在 BOM 导入之前 -->
        <dependency>
            <groupId>com.google.code.gson</groupId>
            <artifactId>gson</artifactId>
            <version>${gson.version}</version>
        </dependency>
        <dependency>
            <groupId>com.baomidou</groupId>
            <artifactId>mybatis-plus-boot-starter</artifactId>
            <version>${mybatis-plus.version}</version>
        </dependency>
        <!-- …easyexcel / hutool-all / commons-collections4 同理… -->

        <!-- 3.2 Spring 生态 BOM：import 进来，全家桶版本自动对齐 -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>${spring-boot.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>org.springframework.cloud</groupId>
            <artifactId>spring-cloud-dependencies</artifactId>
            <version>${spring-cloud.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <dependency>
            <groupId>com.alibaba.cloud</groupId>
            <artifactId>spring-cloud-alibaba-dependencies</artifactId>
            <version>${spring-cloud-alibaba.version}</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>

        <!-- 3.3 项目内部模块：用 ${project.version}，版本随父工程联动 -->
        <dependency>
            <groupId>com.hax</groupId>
            <artifactId>haxoj-backend-service-client</artifactId>
            <version>${project.version}</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

**`dependencyManagement` 与 `<dependencies>` 的本质区别**：

| | `dependencyManagement` | `<dependencies>` |
|---|---|---|
| 是否真正引入 jar | **否**，只登记版本 | **是**，直接引入 |
| 子模块是否自动获得 | 否，子模块要自己写 `<dependency>` 但不写 `<version>` | **是，无条件继承** |
| 用途 | 版本仲裁台 | 声明“我这个模块真的要用” |

一句话记住：**`dependencyManagement` 负责“定规则”，`<dependencies>` 负责“下单”**。

三个 BOM 用 `<type>pom</type><scope>import</scope>` 一次性导入后：

- `spring-boot-starter-web`、`spring-boot-starter-test`、`lombok`、`commons-lang3`(3.12.0)、`mysql-connector-j`(8.0.31) 等版本**全部不用再写**；
- `spring-cloud-starter-gateway`、`spring-cloud-starter-openfeign` 由 cloud BOM 管；
- `nacos-discovery`、`sentinel` 由 alibaba BOM 管（2021.0.5.0 → nacos-client 2.2.0 / sentinel 1.8.6）。

### ④ `<dependencies>`：只放“人人需要且无副作用”的东西

```xml
<dependencies>
    <!-- 与业务无关的通用工具库：网关/公共库继承也无副作用 -->
    <dependency><groupId>org.apache.commons</groupId><artifactId>commons-lang3</artifactId></dependency>
    <dependency><groupId>com.google.code.gson</groupId><artifactId>gson</artifactId></dependency>
    <dependency><groupId>cn.hutool</groupId><artifactId>hutool-all</artifactId></dependency>
    <dependency><groupId>org.apache.commons</groupId><artifactId>commons-collections4</artifactId></dependency>
    <!-- 编译期 / 测试期通用 -->
    <dependency><groupId>org.projectlombok</groupId><artifactId>lombok</artifactId><optional>true</optional></dependency>
    <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-test</artifactId><scope>test</scope></dependency>
</dependencies>
```

**这里千万不能图省事把 Web / MyBatis / Nacos 也塞进来。** 这是本次改造最关键的判断：父工程 `<dependencies>` 是“无条件下发”的，塞进去的依赖会落到**每一个**子模块头上，包括不该有 Web 的网关和公共库。所以本项目只把“任何模块都可能用、且不会引发冲突”的工具类库和 lombok/test 放在这里。

> 判断标准：**如果某个依赖会让别的模块产生编译/启动冲突，或者业务上它根本不该出现，就不要放父工程 `<dependencies>`，改用 `dependencyManagement` + 子模块按需声明。**

### ⑤ `<pluginManagement>`：锁插件版本，但不强制启用

```xml
<build>
    <pluginManagement>
        <plugins>
            <plugin>
                <groupId>org.apache.maven.plugins</groupId>
                <artifactId>maven-compiler-plugin</artifactId>
                <version>3.8.1</version>
                <configuration>
                    <source>${java.version}</source>
                    <target>${java.version}</target>
                    <encoding>${project.build.sourceEncoding}</encoding>
                </configuration>
            </plugin>
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
                <version>${spring-boot.version}</version>
                <executions>
                    <execution>
                        <id>repackage</id>
                        <goals><goal>repackage</goal></goals>
                    </execution>
                </executions>
            </plugin>
        </plugins>
    </pluginManagement>
</build>
```

- 用 `pluginManagement` 而不是 `<build><plugins>`：**只统一定义版本和默认配置，是否真启用由子模块决定**。公共库不需要打可执行包，就永远不引 `spring-boot-maven-plugin`。
- `repackage` 这个 `<execution>` 必须显式写。它不像 `spring-boot-starter-parent` 那样自动带上；本项目第一次构建时就是漏了它，4 个服务全部打出 10KB 的“空壳 jar”，加上之后才有 46–66MB 的 fat jar。

## 四、子模块 pom.xml 怎么写

子模块的模板就三段：`<parent>` + 自己坐标 + 自己真正需要的依赖。

### 4.1 公共库类模块（`common` / `model`）——最简

```xml
<parent>
    <groupId>com.hax</groupId>
    <artifactId>haxoj-backend-microservice</artifactId>
    <version>0.0.1-SNAPSHOT</version>
</parent>

<artifactId>haxoj-backend-common</artifactId>
<name>haxoj-backend-common</name>
<description>公共模块：统一返回对象、错误码、全局异常与通用工具类</description>
```

不带 `<version>`（从父工程继承）、不带 `<build>`、不引 Web。`lombok`、`commons-lang3`、`hutool` 等已在父工程 `<dependencies>` 里，这里不用重复声明。

### 4.2 客户端库模块（`service-client`）——引入 Feign

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.cloud</groupId>
        <artifactId>spring-cloud-starter-openfeign</artifactId>
    </dependency>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <!-- 内部模块：不写版本号，走父工程 dependencyManagement -->
    <dependency><groupId>com.hax</groupId><artifactId>haxoj-backend-common</artifactId></dependency>
    <dependency><groupId>com.hax</groupId><artifactId>haxoj-backend-model</artifactId></dependency>
</dependencies>
```

### 4.3 可执行服务模块（`gateway` / `user` / `question` / `judge`）

以 `question-service` 为例：

```xml
<dependencies>
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-web</artifactId>
    </dependency>
    <dependency>
        <groupId>com.alibaba.cloud</groupId>
        <artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId>
    </dependency>
    <dependency>
        <groupId>com.alibaba.cloud</groupId>
        <artifactId>spring-cloud-starter-alibaba-sentinel</artifactId>
    </dependency>
    <dependency>
        <groupId>com.baomidou</groupId>
        <artifactId>mybatis-plus-boot-starter</artifactId>
    </dependency>
    <dependency>
        <groupId>com.mysql</groupId>
        <artifactId>mysql-connector-j</artifactId>
        <scope>runtime</scope>
    </dependency>
    <dependency>
        <groupId>com.alibaba</groupId>
        <artifactId>easyexcel</artifactId>   <!-- 只有题目批量导入用，按需声明 -->
    </dependency>
    <!-- 内部模块 -->
    <dependency><groupId>com.hax</groupId><artifactId>haxoj-backend-common</artifactId></dependency>
    <dependency><groupId>com.hax</groupId><artifactId>haxoj-backend-model</artifactId></dependency>
    <!-- 开发期热部署：runtime + optional，不传递 -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-devtools</artifactId>
        <scope>runtime</scope>
        <optional>true</optional>
    </dependency>
</dependencies>

<build>
    <plugins>
        <!-- 可执行服务才引这个插件，版本从父工程 pluginManagement 继承 -->
        <plugin>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-maven-plugin</artifactId>
        </plugin>
    </plugins>
</build>
```

网关模块（`gateway`）的特殊处理——**绝不能引 `spring-boot-starter-web`**：

```xml
<dependencies>
    <dependency><groupId>org.springframework.cloud</groupId><artifactId>spring-cloud-starter-gateway</artifactId></dependency>
    <dependency><groupId>com.alibaba.cloud</groupId><artifactId>spring-cloud-starter-alibaba-nacos-discovery</artifactId></dependency>
    <dependency><groupId>com.alibaba.cloud</groupId><artifactId>spring-cloud-starter-alibaba-sentinel</artifactId></dependency>
    <dependency><groupId>com.alibaba.cloud</groupId><artifactId>spring-cloud-alibaba-sentinel-gateway</artifactId></dependency>
</dependencies>
```

验证结果：`mvn dependency:tree` 里网关只有 `spring-cloud-starter-gateway → spring-boot-starter-webflux → spring-webflux`，**没有任何 `spring-boot-starter-web` / `spring-webmvc`**，从依赖层面杜绝了“Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway”这个启动即崩的问题。

### 4.4 三类模块对照表

| 模块 | 类型 | 是否引 Web | 是否引 Boot 打包插件 | 依赖来源 |
|---|---|---|---|---|
| `haxoj-backend-common` | 公共库 | 否 | 否 | 仅父工程通用依赖 |
| `haxoj-backend-model` | 公共库 | 否 | 否 | 仅父工程通用依赖 |
| `haxoj-backend-service-client` | 客户端库 | Web + OpenFeign | 否 | 父工程 + 内部模块 |
| `haxoj-backend-gateway` | 可执行服务 | WebFlux（由 gateway starter 带） | 是 | 父工程 + Gateway/Nacos/Sentinel |
| `haxoj-backend-user-service` | 可执行服务 | 是（MVC） | 是 | 父工程 + Web/Nacos/Sentinel/MyBatis-Plus/MySQL |
| `haxoj-backend-question-service` | 可执行服务 | 是（MVC） | 是 | 同上 + EasyExcel |
| `haxoj-backend-judge-service` | 可执行服务 | 是（MVC） | 是 | 同上 + OpenFeign + service-client |

## 五、本项目踩过的坑（都有实测依据）

### 坑 1：只聚合不继承，或只继承不聚合

改造前 `service-client`～`judge-service` 既没进 `<modules>`、也没写 `<parent>`，完全是 5 个独立工程。**两个都要配**，缺一个就会出现“改了父工程，子模块没生效”或“单模块能编译，全量构建跳过它”的灵异现象。

### 坑 2：BOM 放错位置

`spring-cloud-dependencies` 被写在父工程 `<dependencies>` 里，还带着 `<type>pom</type><scope>import</scope>`。这不是它的位置——带 `import` 的 BOM 只对 `dependencyManagement` 有意义。放在 `<dependencies>` 里既不生效，又会让读代码的人以为“版本已经管好了”。

### 坑 3：子模块偷偷覆盖父工程管的版本

改造前每个子模块都自带一份 `dependencyManagement`。**子模块自己声明的 `dependencyManagement` 优先级高于父工程**，于是父工程统一管好的版本被无声覆盖，`spring-cloud 2021.0.5` 和 `2021.0.5.0` 就是这么来的。改造后子模块的 `dependencyManagement` 全部删除。

### 坑 4：父工程 `<dependencies>` 的无条件下发

父工程原先的下发列表里有 Web、MyBatis、Nacos、MySQL。一旦 `gateway` 挂上父工程，它会**被迫**拿到 `spring-boot-starter-web`，与 Gateway 的 WebFlux 冲突。改为：通用工具类库才进 `<dependencies>`，业务/技术栈相关的一律进 `dependencyManagement`，由子模块按需声明。

### 坑 5：BOM 导入顺序会吃掉你的显式版本（最隐蔽）

`spring-boot-dependencies:2.6.13` 里 gson 管理的是 `2.8.9`，而本项目需要 `2.9.1`。规则是：**合并 `dependencyManagement` 时“先声明者优先”**，import 进来的 BOM 相当于就地展开。

```xml
<!-- ✗ 这样写，gson 会被 BOM 的 2.8.9 覆盖 -->
<dependency> spring-boot-dependencies import … </dependency>
<dependency> gson <version>${gson.version}</version> </dependency>

<!-- ✓ 显式版本写在 BOM 之前，才拿得到 2.9.1 -->
<dependency> gson <version>${gson.version}</version> </dependency>
<dependency> spring-boot-dependencies import … </dependency>
```

实测：按 ✓ 的方式，`dependency:tree` 输出 `com.google.code.gson:gson:jar:2.9.1:compile`。

> 顺带一个常见误区：在父工程 `<properties>` 里写 `<gson.version>2.9.1</gson.version>` 想覆盖 BOM，**在 import BOM 的模式下是无效的**（那只对 `spring-boot-starter-parent` 这种“继承父 POM”的方式有效）。要么按上面调整顺序，要么显式声明。

### 坑 6：`repackage` 执行没绑定 → 打出空壳 jar

`spring-boot-maven-plugin` 的 `repackage` 目标**不会**因为你引了插件就自动执行（只有在用 `spring-boot-starter-parent` 时才自带这个 execution）。本项目第一次全量构建“BUILD SUCCESS”，但 4 个服务的 jar 只有 ~10KB，里面根本没有依赖。

修法：在父工程 `pluginManagement` 里补上 `<executions><execution><id>repackage</id><goals><goal>repackage</goal></goals></execution></executions>`。修复后 jar 体积 46–66MB，`Replacing main artifact with repackaged archive` 正常出现。

**排查口诀：构建成功 ≠ 产物可用。打完包一定要看 jar 体积。**

### 坑 7：重复引入 MyBatis 的两个 starter

`mybatis-spring-boot-starter` 与 `mybatis-plus-boot-starter` 功能重叠（MyBatis-Plus starter 已包含 mybatis-spring）。本项目移除前者，只保留 MyBatis-Plus，`@MapperScan` 等注解照常可用。

### 坑 8：编译级别不一致

`common`/`model` 写死 `maven.compiler.source/target=11`，父工程是 `1.8`。同一工程两种级别，容易在跨模块调用时炸出 `Unsupported class file major version`。统一由父工程 `${java.version}` 驱动，子模块不再各自设。

> 补充：`source/target` 与 `release` 是两回事。`release` 会连 JDK 内置 API 也按目标版本校验（更严格，推荐新项目用 `<release>`）；老项目沿用 `source/target` 也行。本机用 JDK 21 执行 `source/target=1.8` 可正常编译，只是会有 obsolete 警告。

### 坑 9：内部模块依赖写死版本

子模块之间引用必须写

```xml
<dependency><groupId>com.hax</groupId><artifactId>haxoj-backend-model</artifactId></dependency>
```

**不写 `<version>`**，版本来自父工程 `dependencyManagement` 里的 `${project.version}`。这样以后统一升版本（如 `0.1.0`）只改父工程一处，7 个子模块全跟着走。

## 六、企业级微服务项目的 Maven 通用规范

### 6.1 依赖范围（scope）管控

| scope | 参与的类路径 | 是否传递给下游模块 | 典型用途 |
|---|---|---|---|
| `compile`（默认） | 编译 + 测试 + 运行 | 是 | 业务代码直接使用的库（spring-boot-starter-*） |
| `provided` | 编译 + 测试 | 否 | 由容器/JDK 提供：`lombok`、`servlet-api` |
| `runtime` | 测试 + 运行 | 是 | 运行时才需要：`mysql-connector-j`、JDBC 驱动 |
| `test` | 测试 | 否 | `spring-boot-starter-test`、`junit` |
| `import` | —（仅 pom） | — | 只在 `dependencyManagement` 中导 BOM |
| `optional=true` | 编译+测试+运行（本模块） | 否 | `devtools`；不希望被下游传递的依赖 |

原则：**能用更小的 scope 就用更小的**。驱动用 `runtime`、测试用 `test`、热部署用 `runtime + optional`，既减小产物，也避免把不该暴露的 API 传给别人。

### 6.2 公共抽取模块的设计

本项目抽了三层，自上而下：

```
haxoj-backend-common         全局返回对象 BaseResponse、错误码、自定义异常、工具类
haxoj-backend-model          实体 / DTO / VO / 枚举（跨服务共享的领域模型）
haxoj-backend-service-client 服务对外契约：Feign 接口 + 入参出参 DTO
```

实践建议：

- **公共模块不引 Web/DB starter**，只依赖 lombok、工具库等轻量依赖，防止“抽个 common 结果把整个 Spring Web 拖进来”。
- **依赖方向必须单向**：`common ← model ← service-client ← 各服务`。一旦出现 `common` 反过来依赖某个服务，就是循环依赖，`mvn` 直接在 reactor 排序阶段报错。
- 服务之间**不共享实现代码**，只共享 `service-client` 里的接口契约，避免分布式“共享库地狱”。
- 更细的拆分（如 `api` / `util` / `security`）在中大型团队很常见，但**模块数量不是越多越好**，每个模块都要有清晰的职责边界。

### 6.3 插件统一配置

- **全部用 `pluginManagement` 锁版本**，`<build><plugins>` 只出现在真正需要的模块。否则 Maven 会警告 “plugin version not specified”，且不同环境可能拉到不同版本。
- 常用插件及其企业级用途：

| 插件 | 用途 |
|---|---|
| `maven-compiler-plugin` | 统一 `source/target/encoding`（本项目已配） |
| `spring-boot-maven-plugin` | 可执行服务打 fat jar（本项目已配，仅服务模块启用） |
| `maven-surefire-plugin` | 统一单测执行、并行、`-DskipTests` 之外的开关 |
| `maven-enforcer-plugin` | **强烈推荐**：`requireMavenVersion`、`banDuplicatePomDependencyVersions`、`dependencyConvergence`，把版本冲突拦在构建期 |
| `maven-dependency-plugin` | `dependency:analyze` 查“声明了没用/用了没声明”的依赖 |
| `flatten-maven-plugin` | 配合 `${revision}` 做多模块统一发版 |
| `jacoco-maven-plugin` | 覆盖率门禁 |

- 公共库模块**不要**引 `spring-boot-maven-plugin`：本项目 `common`/`model` 就保持普通 jar（实测 `.jar` 只有几十 KB），这样才能被其它模块当依赖引用。

### 6.4 多模块构建命令速查

在父工程根目录执行：

| 命令 | 作用 |
|---|---|
| `mvn clean package` | 全量清理 + 打包（父工程聚合了所有子模块） |
| `mvn -DskipTests package` | 跳过测试打包（本项目验证用的就是这个） |
| `mvn install` | 安装到本地仓库，供其它工程引用 |
| `mvn -pl haxoj-backend-question-service -am package` | **只构建某模块及其上游依赖**（`-am` = also make） |
| `mvn -pl haxoj-backend-question-service -amd package` | 构建该模块**及其下游**依赖 |
| `mvn -pl haxoj-backend-gateway -am -DskipTests package` | 只重启/重建网关这一条链，微服务开发最常用 |
| `mvn -rf haxoj-backend-judge-service package` | 从失败处续跑（`-rf` = resume from） |
| `mvn -T 4 clean package` | 4 线程并行构建，模块多时提速 |
| `mvn dependency:tree` | 查看依赖树，排冲突 |
| `mvn dependency:tree -Dincludes=com.google.code.gson:gson` | 只看某个依赖从哪来、是哪个版本 |
| `mvn help:effective-pom` | 看“真正生效”的 POM（继承/覆盖后），排查配置为何没生效的终极手段 |
| `mvn versions:set -DnewVersion=0.1.0` | 批量改所有模块版本号 |

> 开发微服务时，`mvn -pl <模块> -am -DskipTests package` 是最实用的命令：只编译你改动的那条依赖链，比全量快得多。

### 6.5 版本统一与发版（进阶）

模块多、发版频繁时，推荐用 `${revision}` + `flatten-maven-plugin`：

```xml
<properties>
    <revision>0.0.1-SNAPSHOT</revision>
</properties>
<!-- 父工程与子模块的 version 统一写 ${revision} -->
```

配合 `flatten-maven-plugin` 在打包时把 `${revision}` 解析成确定值，一次命令就能改全工程版本。本项目当前模块规模用不上，但值得知道。

### 6.6 与 CI 的衔接

- 构建命令统一走父工程根目录的 `mvn -B -DskipTests clean package`，`-B` 批处理模式，避免 CI 交互卡住。
- CI 缓存 `.m2/repository`，增量构建。
- 建议在父工程开启 `maven-enforcer-plugin`，把依赖冲突、Maven 版本不符直接拦在流水线而不是运行时。

## 八、给后续模块的落地清单

新增一个微服务模块时，按这个清单走：

1. 在 `haxoj-backend-microservice/` 下建目录，`pom.xml` 第一段写 `<parent>`（三行坐标）。
2. 只写自己的 `<artifactId>`、`<name>`、`<description>`，**不写** `<groupId>`、`<version>`、`<properties>`。
3. 需要的新第三方依赖：先把版本属性加进父工程 `<properties>`，再决定放父工程 `<dependencyManagement>`（非 Spring 生态）还是交给 BOM（Spring 生态）。
4. 依赖清单里**一律不写 `<version>`**；内部模块依赖也不写。
5. 是可执行服务 → 加 `<build><plugins>` 引 `spring-boot-maven-plugin`；是公共库 → 什么都不加。
6. 回父工程 `<modules>` 补一行。
7. 验证：`mvn -pl <新模块> -am -DskipTests package`，**并检查产出的 jar 体积是否符合预期**。

## 九、一句话总结

父工程是“规则制定者”，子模块是“具体消费者”：

- 版本、编码、编译级别、插件版本 → 全部收在父工程（`<properties>` + `<dependencyManagement>` + `<pluginManagement>`）；
- 子模块只声明“我要什么”，永远不写“我要哪版”；
- 只有真正人人适用、无副作用的依赖才放父工程 `<dependencies>`，其余一律按需声明——尤其是 Web 和网关，绝不能无脑下发。

## 十、依赖版本到底从哪来：dependencyManagement、BOM 与 `import`

这是本次改造中最容易被“写对了但没看懂”的部分。父工程 `<dependencies>` 里 `commons-lang3`、`lombok`、`spring-boot-starter-test` 这些**既没写 `<version>`，也没在本工程 `<dependencyManagement>` 里出现**，那版本是从哪里冒出来的？

### 10.1 版本只有三个来源

Maven 解析任意一个依赖的版本时，只会去这三个地方找，且严格按此优先级：

1. **依赖自己写的 `<version>`** —— 最高优先级，谁写谁说了算（本项目已刻意不写）。
2. **一张“版本表”** —— 即 `<dependencyManagement>`。它由你们的 POM 自我声明 + 从父工程继承 + **通过 `import` 引入的 BOM** 合并而成。
3. **都没有** —— Maven 报 `'dependencies.dependency.version' for X:jar is missing`，构建中断。

所以 `commons-lang3` 属于第 2 类：它的版本由 **spring-boot-dependencies 这个 BOM** 提供，本工程一个字都不用写。

### 10.2 什么是 BOM（Bill of Materials，物料清单）

- BOM 就是一个 `<packaging>pom</packaging>` 的、几乎只包含 `<dependencyManagement>` 的 POM。
- 它**不产出任何代码**，唯一职责是：替**一整套库**预先登记好版本。
- 举例：`spring-boot-dependencies:2.6.13` 内部实际就写了（实测从其 POM 中读到的属性）：

| BOM 内部属性 | 值 |
|---|---|
| `<commons-lang3.version>` | `3.12.0` |
| `<lombok.version>` | `1.18.24` |
| `<mysql.version>` | `8.0.31` |
| `<gson.version>` | `2.8.9` ← 注意这个值 |
| `<spring-framework.version>` | `5.3.23` |

并在它自己的 `<dependencyManagement>` 里为 commons-lang3、lombok、mysql-connector-j、spring-boot-starter-* 等登记了版本。于是你写

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-lang3</artifactId>
</dependency>
```

不写版本也能解析——**版本是 BOM “带进来”的**。

### 10.3 为什么需要 `<type>pom</type><scope>import</scope>`

- POM 的 `<parent>` 是单继承：一个工程**只能有一个父 POM**。
- 但本项目需要同时用 Boot、Cloud、Alibaba 三张版本表，靠继承根本做不到。
- Maven 因此提供了 `import`：把**别人 POM 的 `<dependencyManagement>` 抄进我自己的 `<dependencyManagement>`**（只抄版本表，不继承其它配置）。

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-dependencies</artifactId>
    <version>${spring-boot.version}</version>
    <type>pom</type>
    <scope>import</scope>   <!-- 关键：语义是"并入我的版本表" -->
</dependency>
```

最终形成**一张属于本工程的版本表**，它有两个来源：

```
Spring Boot BOM ┐
Spring Cloud BOM ├─ import ─┐
Alibaba BOM     ┘          ├─▶  父工程 dependencyManagement（版本表）
本工程手写条目 ────────────┘                  │
                                               ▼
                                子模块里不写 <version> 的 <dependency>
```

### 10.4 本工程依赖 → 版本来源对照表（实测）

| 依赖 | 解析版本 | 来源 |
|---|---|---|
| `commons-lang3` | 3.12.0 | spring-boot BOM（自动带入，无需声明） |
| `lombok` | 1.18.24 | spring-boot BOM |
| `spring-boot-starter-test` | 随 Boot 2.6.13 | spring-boot BOM |
| `mysql-connector-j` | 8.0.31 | spring-boot BOM |
| `spring-cloud-starter-gateway` | 3.1.4 | spring-cloud BOM |
| `spring-cloud-starter-openfeign` | 随 Cloud 2021.0.5 | spring-cloud BOM |
| `nacos-client` | 2.2.0 | alibaba BOM 2021.0.5.0 |
| `sentinel-*` | 1.8.6 | alibaba BOM 2021.0.5.0 |
| `gson` | **2.9.1** | **本工程手写条目**（覆盖 BOM 的 2.8.9） |
| `hutool-all` | 5.8.8 | 本工程手写条目 |

### 10.5 一条最实用的判断经验

**“这个依赖要不要我自己在 `<dependencyManagement>` 里写一条？”**

- 它**在某个 BOM 里**（Spring / Cloud / Alibaba 生态的绝大多数都在）→ **不用写**，import BOM 即可。
- 它**不在任何 BOM 里**（hutool、easyexcel、commons-collections4、MyBatis-Plus、gson 的自定义版本…）→ **必须写**，否则子模块一引用就报 `version is missing`。

这也解释了父工程 `<dependencyManagement>` 里为什么只有那 5 条手写条目：其余版本都被三张 BOM 包了。

### 10.6 “Spring 生态”为什么要成套使用

Boot ↔ Cloud ↔ Alibaba 之间存在严格的**兼容矩阵**（本项目为 Boot `2.6.13` ↔ Cloud `2021.0.5` ↔ Alibaba `2021.0.5.0`）。任意一个对不上，就会出现 `NoSuchMethodError`、自动配置失效、启动即崩等诡异问题。BOM 的价值就是**把一整套已验证匹配的版本打包给你**——你只需决定 import 哪一版 BOM，而不用逐个库去凑版本。这就是“生态依赖”的含义：它们不是零散的三方库，而是**必须整体对齐的版本集合**。

### 10.7 三个高频误区

| 误区 | 事实 |
|---|---|
| 在父工程 `<properties>` 写 `<gson.version>2.9.1</gson.version>` 想覆盖 import 的 BOM | **无效**。`<scope>import</scope>` 的 BOM 用自己的属性插值；只有“继承 `spring-boot-starter-parent`”那种模式下，子/父 POM 的属性覆盖才生效。想改版本要么把显式条目写在 BOM 之前，要么直接声明带版本的依赖 |
| 把 `<scope>import</scope>` 写在 `<dependencies>` 里 | 无效且无意义。import 只对 `<dependencyManagement>` 有意义 |
| 以为“不写版本 = 用最新版” | 错。**Maven 从不自动挑最新版**，版本必须由 `<dependencyManagement>` 明确给出，给不出就构建失败 |

> 一句话：`<dependencies>` 决定“要不要这个 jar”，`<dependencyManagement>`（含 BOM）决定“用哪个版本”。没有版本表的无版本依赖 = 构建报错。

## 十一、`${project.version}` 这类内置表达式从哪来

父工程 `<dependencyManagement>` 里的内部模块依赖写的是：

```xml
<dependency>
    <groupId>com.hax</groupId>
    <artifactId>haxoj-backend-common</artifactId>
    <version>${project.version}</version>   <!-- 注意：它不在 <properties> 里 -->
</dependency>
```

`${project.version}` **不是** `<properties>` 定义的属性，而是 Maven 的**内置模型表达式（model interpolation）**，取自 POM 自己的 `<version>` 元素（本工程即 `0.0.1-SNAPSHOT`）。
实测：`mvn help:effective-pom -pl haxoj-backend-judge-service` 输出的该依赖版本正是 `0.0.1-SNAPSHOT`。

要点：

- `project.*` 是一组内置表达式，不占用 `<properties>` 命名空间，常见还有：`${project.groupId}`、`${project.artifactId}`、`${project.packaging}`、`${project.basedir}`、`${project.build.directory}`、`${project.build.finalName}`。
- 别名：`${version}`、`${pom.version}` 等价，但属于旧写法，不推荐。
- **为什么能“自动联动”**：所有子模块都没自己声明 `<version>`，而是继承父工程的同一个版本，因此把内部模块版本写成 `${project.version}`，父工程升版本时 7 个子模块会一起变。这也正是多模块**必须保持版本一致**的原因。
- **使用禁区**：`${project.version}` 不能用在 `<parent><version>` 里（自己引用自己，循环）。跨模块统一发版场景下，更推荐 CI 友好的 `${revision}` + `flatten-maven-plugin`。
- **验证方法**：`mvn help:effective-pom` 看到的是“继承合并 + 插值之后”真正生效的 POM，是排查“某个 `${xxx}` 到底解析成什么”的终极手段。
