# HaxOJ 微服务启动类注解规范笔记

> 这份笔记回答一个问题：**Spring Boot 业务模块的启动类上到底该写哪些注解？**
> 参照物是鱼皮官方微服务版 `yuoj` 的 user-service 启动类（注解一大堆），
> 对照咱们 `haxoj-backend-microservice` 的启动类（注解很少），
> 逐条分析「为什么人家写那么多」「为什么我们不用写」「我们在什么情况下必须补」。

---

## 一、先对齐参照物

### 1. 鱼皮官方微服务版 `yuoj` 的 user-service 启动类

```java
@SpringBootApplication
@MapperScan("com.yupi.yuojbackenduserservice.mapper")
@EnableScheduling
@EnableAspectJAutoProxy(proxyTargetClass = true, exposeProxy = true)
@ComponentScan("com.yupi")
@EnableDiscoveryClient
public class YuojBackendUserServiceApplication {
    public static void main(String[] args) {
        SpringApplication.run(YuojBackendUserServiceApplication.class, args);
    }
}
```

### 2. 咱们项目的现状

| 模块 | 启动类路径 | 现有注解 |
| --- | --- | --- |
| user-service | `haxoj-backend-user-service/.../HaxojBackendUserServiceApplication.java` | `@SpringBootApplication` |
| question-service | `haxoj-backend-question-service/.../HaxojBackendQuestionServiceApplication.java` | `@SpringBootApplication` + `@EnableFeignClients` |
| judge-service | `haxoj-backend-judge-service/.../HaxojBackendJudgeServiceApplication.java` | `@SpringBootApplication` + `@EnableFeignClients` |
| gateway | `haxoj-backend-gateway/.../HaxojBackendGatewayApplication.java` | `@SpringBootApplication` |

```java
// 咱们的 user-service：干净到只有一行
@SpringBootApplication
public class HaxojBackendUserServiceApplication { ... }
```

**一句话结论**：咱们不是漏写了注解，而是**用"统一包名 + 公共配置集中承载"换掉了那堆开关注解**。
但这个"少"依赖两条**隐式约定**，必须写进规范，否则以后新建模块会踩坑（见第三节末）。

## 二、主流项目启动类常见注解：作用、场景、必要性

**核心认知：只有 `@SpringBootApplication` 是"人人必备"，其余都是"功能开关"——用了对应功能才需要打开。**

| 注解 | 本质作用 | 典型场景 | 必要性 |
| --- | --- | --- | --- |
| `@SpringBootApplication` | 复合注解 = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`（默认扫**启动类所在包及其子包**） | 所有 Boot 应用 | **必须，唯一不可省** |
| `@ComponentScan("com.x")` | 把扫描根从「启动类所在包」改到别的包 | 各模块**包名不共享同一根包**时 | 视包结构，可能必须 |
| `@MapperScan("...mapper")` | 扫描 Mapper 接口，为每个接口生成 Mapper 代理 Bean | 用 MyBatis / MyBatis-Plus，且接口上**没写 `@Mapper`** | 用 MyBatis 时必要（**可放在 `@Configuration` 类上，不必写在启动类**） |
| `@EnableDiscoveryClient` | 声明"本应用是注册中心客户端"，触发服务注册 | 早期 Spring Cloud 必写 | **可选**：新版 Spring Cloud 默认自动注册，写了只是语义更清晰 |
| `@EnableFeignClients` | 扫描 `@FeignClient` 接口并生成动态代理 Bean | **需要调用别的服务**的一方 | 消费方**必须** |
| `@EnableAspectJAutoProxy(proxyTargetClass, exposeProxy)` | 开启 AspectJ 自动代理；`exposeProxy=true` 让 `AopContext.currentProxy()` 可用 | 需要让"类内自调用"也走代理（**事务/异步自调用失效**的经典场景） | **默认已开**：Boot 的 `AopAutoConfiguration` 在 classpath 有 AspectJ 时自动开启；只有 `exposeProxy` 才需显式写 |
| `@EnableScheduling` | 开启 `@Scheduled` 定时任务 | 有定时任务（缓存同步、统计报表、ES 同步等） | 有任务时**必须**，没有则无用 |
| `@EnableAsync` | 开启 `@Async` 异步方法 | 有异步执行需求 | 有 `@Async` 时**必须**（否则 `@Async` 静默失效） |
| `@EnableTransactionManagement` | 开启注解式事务 | 用 `@Transactional` | Boot 检测到 `DataSource` 时**已自动开启**，通常无需手写 |
| `@EnableCaching` | 开启 Spring Cache 注解 | 用 `@Cacheable` / `@CacheEvict` | 用时**必须** |
| `@ConfigurationPropertiesScan` | 扫描 `@ConfigurationProperties` 配置类 | 配置类没标 `@Component` | 视写法 |

## 三、咱们注解少的原因：合理简化，还是隐患？

**结论：是架构层面的合理简化**，每一条都有代码依据（已逐一核实）：

| 参照项目的注解 | 咱们是否需要 | 依据 |
| --- | --- | --- |
| `@ComponentScan("com.yupi")` | **不需要** | 咱们**所有模块统一基础包 `com.hax.haxojbackend`**（服务、common、model、service-client 全在这个根下），启动类本身就在 `com.hax.haxojbackend`，默认扫描范围天然覆盖全部。鱼皮项目是因为业务包 `com.yupi.yuojbackenduserservice` 与公共包 `com.yupi.yuojbackendcommon` **不同根**，才必须靠 `@ComponentScan("com.yupi")` 把公共配置扫进来 |
| `@MapperScan("...mapper")` | **不需要在启动类写，但功能没丢** | 它已经在 `haxoj-backend-common/.../config/MyBatisPlusConfig.java` 上，且该配置类会被扫描加载；`com.hax.haxojbackend.mapper` 正好覆盖 `UserMapper`、`QuestionMapper`、`QuestionSubmitMapper` 三个接口（它们都是 `extends BaseMapper`、**没有 `@Mapper` 注解**，完全依赖扫描） |
| `@EnableScheduling` | **不需要** | 全项目搜不到任何 `@Scheduled`；帖子/ES 同步的 `job` 包在拆分时已删除 |
| `@EnableAspectJAutoProxy` | **不需要** | ① `@Aspect` 代理 Boot 默认已开——`AuthInterceptor`（user/question）和 `LogInterceptor`（common）能正常工作就是证据；② Boot 默认已是 CGLIB（等价于 `proxyTargetClass=true`）；③ `exposeProxy=true` 只在代码用 `AopContext.currentProxy()` 时才需要，**全项目没有用到** |
| `@EnableDiscoveryClient` | **可选，不写也能注册** | 三个服务都引了 `spring-cloud-starter-alibaba-nacos-discovery`，Spring Cloud Commons 默认自动注册；实测三个服务**没写这个注解也全部注册进了 Nacos** |
| `@EnableFeignClients` | **该写的都写了** | 调用矩阵是 question→(user+judge)、judge→question，所以 question、judge 各写了；user-service **只做提供方、不调别人**（pom 里也没有 `spring-cloud-starter-openfeign`），**不写才是正确** |

### 但有两条「隐式约定」是潜在风险，必须知道

**风险 1：「包名统一」是全局扫描成立的前提。**

一旦以后新建模块用了别的根包，就成了参照项目那种情况——common 里的 `MyBatisPlusConfig`、`CorsConfig`、`LogInterceptor`、全局异常处理器**会静默扫不到**。
报错信息很隐晦：不是"缺注解"，而是**分页插件失效 / 跨域失效 / 异常没被统一包装**。

> 现在已经有一个反例：`HaxojBackendGatewayApplication` 的包是 `com.hax.haxojbackendgateway`，**不在** `com.hax.haxojbackend` 根下。
> **但这对网关本身是"对的"**——网关基于 WebFlux，**绝不能**扫进 common 里依赖 Spring MVC 的 `CorsConfig`，否则启动冲突。
> 所以结论不是「给网关加 `@ComponentScan`」，而是「**网关不能复用 common**」。

**风险 2：`@MapperScan` 只有一处，且写死了包路径 `com.hax.haxojbackend.mapper`。**

以后某模块新增 Mapper 却放在别的包（例如 `com.hax.haxojbackend.user.mapper`），
**编译期不报错，运行期才炸**：典型症状 `Invalid bound statement (not found)` 或注入不到 Mapper Bean。
这是最容易被忽略的配置遗漏。

### 顺带：gateway 模块的清理项

gateway 现在仍残留脚手架文件（`demos/web/BasicController.java`、`demos/web/PathVariableController.java`、`static/index.html`、`application.properties`），
与「网关尚未实现」的现状不符，建议清理（属清理项，不是注解问题）。

## 四、必须补充 / 可选添加 / 不建议

### 1. 必须补充：**当前三个业务服务 = 零**

三个服务的注解配置**在功能上是完整的**（验证见第六节）。
真正要"补"的不是注解，而是把第三节末的两条约定写进规范。

### 2. 可选添加（按需，加了也无害）

| 注解 | 加到谁 | 收益 | 潜在影响 |
| --- | --- | --- | --- |
| `@EnableDiscoveryClient` | user / question / judge / gateway | 语义自文档化：一眼看出"这是注册中心客户端"；兼容老版写法 | **无副作用**（等于把默认行为显式化）。**可选，非必须** |
| `@EnableFeignClients(basePackages = "com.hax.haxojbackend")` | question / judge | 显式声明扫描范围，避免以后启动类挪包导致契约扫不到 | 无 |
| `@EnableScheduling` | 未来有定时任务的模块 | 开启 `@Scheduled` | 加了但没任务，无害；反之**没加却写了 `@Scheduled` 会静默不执行** |
| `@EnableAsync` | 未来有 `@Async` 的模块 | 开启异步 | 需自配线程池，否则默认 `SimpleAsyncTaskExecutor`，高并发下线程暴涨 |
| `@EnableCaching` | 用 Spring Cache 时 | 开启缓存注解 | 需选缓存实现（本项目已有 Redis） |
| `@EnableAspectJAutoProxy(exposeProxy = true)` | 仅当引入 `AopContext.currentProxy()` 自调用 | 解决事务/异步自调用失效 | 显式暴露代理，轻微开销；**无自调用需求时不要加** |

### 3. 明确不建议（反面清单）

- ❌ 在启动类重复写 `@MapperScan`（与 common 的重复，易冲突）→ 统一放 `@Configuration` 类。
- ❌ 加 `@ComponentScan`（包根统一，加了反而可能漏扫或扫进不该扫的包）。
- ❌ 无脑加 `@EnableTransactionManagement`、`@EnableAspectJAutoProxy`（Boot 默认已开，属噪音）。

## 五、标准化规范（后续新模块照抄）

### 规则 A：注解分层，"三行以内"

```
业务服务启动类 = @SpringBootApplication
              + @EnableFeignClients   ← 仅当本服务要调别的服务
              + @EnableScheduling     ← 仅当本服务有 @Scheduled
```

除此之外，**默认不写任何东西**。

### 规则 B：包名铁律（最重要）

> 所有业务/公共模块一律使用 `com.hax.haxojbackend.*` 包根；启动类放在 `com.hax.haxojbackend`。
> 这样"启动类同包 = 全局配置自动生效"，不需要 `@ComponentScan`。
> **例外：网关用独立包 `com.hax.haxojbackendgateway`，且不得依赖 common**（WebFlux vs Spring MVC 会冲突）。

### 规则 C：Mapper

> Mapper 接口统一放 `com.hax.haxojbackend.mapper`，`@MapperScan` 只在 `MyBatisPlusConfig` **一处**维护。
> 若确实要放到子包，必须同步改 `@MapperScan`，或给接口加 `@Mapper` 兜底。

### 规则 D：只做提供方（被别人调）的服务，不加 `@EnableFeignClients`，也不引 openfeign 依赖

（user-service 就是范例）

### 规则 E：需要"手动开"的功能，注解 + 依赖必须成对出现

| 想用 | 必加注解 | 必加/具备的依赖 |
| --- | --- | --- |
| 跨服务调用 | `@EnableFeignClients` | `spring-cloud-starter-openfeign` **+ `spring-cloud-starter-loadbalancer`** |
| 定时任务 | `@EnableScheduling` | 无额外依赖 |
| 异步 | `@EnableAsync` | 建议自配线程池 |
| 缓存注解 | `@EnableCaching` | 缓存实现（Redis） |

### 规则 F：服务注册

`@EnableDiscoveryClient` 属于**可写可不写**，团队内要统一口径。
建议：**不写**，靠自动注册，减少噪音；若团队推崇"显式优于隐式"，则统一都写。

## 六、功能完整性验证

### 1. 静态核对（逐项有代码依据）

| 依赖功能 | 承载配置 | 现状 |
| --- | --- | --- |
| 自动装配 / 组件扫描 | `@SpringBootApplication` + 统一包根 | ✅ 覆盖 common、model、service-client |
| Mapper Bean 生成 | common 的 `@MapperScan` | ✅ 覆盖 3 个 Mapper |
| 分页插件 | common 的 `MybatisPlusInterceptor` | ✅ 已装配 |
| AOP（日志 / 鉴权） | Boot `AopAutoConfiguration` 默认 | ✅ `@Aspect` 生效 |
| 全局异常 / 统一返回 / 跨域 | common 的 `GlobalExceptionHandler` / `CorsConfig` | ✅ 随扫描生效 |
| Feign 客户端 | question/judge 的 `@EnableFeignClients` | ✅ 契约接口在 `com.hax.haxojbackend` 内，默认扫描覆盖 |
| 服务注册发现 | nacos-discovery starter 自动注册 | ✅ 无需 `@EnableDiscoveryClient` |
| 分布式 session | 各服务 yml `store-type: redis` | ✅ |

### 2. 动态实测（此前已完成，非纸面推断）

- user/question/judge 三个服务**依次成功启动，全部注册进 Nacos**；
- 直接请求 `POST /api/judge/inner/do?questionSubmitId=1`，judge 日志出现
  `For 'haxoj-backend-question-service' URL not provided. Will try picking an instance via load-balancing.`
  → **Feign 跨服务链路打通**（随后抛出的是业务异常"提交信息不存在"，属正常）；
- 期间踩过并解决了 `No Feign Client for loadBalancing defined`（补 `spring-cloud-starter-loadbalancer`）——
  这恰好印证规则 E 里"注解必须与依赖成对"。

### 3. 结论

**现有启动类在当前注解配置下，没有因"缺注解"导致的运行异常或功能失效。**
唯一需要主动防范的是第三节那两条隐式约定（包根 + `@MapperScan` 范围），
它们是"以后新增模块才可能踩"的坑，而非当下的故障。

## 七、速查卡（贴在你的 IDE 备忘里）

```
新建业务服务模块时：
1) 包根必须是 com.hax.haxojbackend，启动类放 com.hax.haxojbackend
2) 启动类只写 @SpringBootApplication
3) 要调别的服务 → 加 @EnableFeignClients + openfeign + loadbalancer
4) 有定时任务 → 加 @EnableScheduling
5) Mapper 放 com.hax.haxojbackend.mapper，别改 @MapperScan
6) 不要加 @ComponentScan / @MapperScan / @EnableAspectJAutoProxy / @EnableTransactionManagement
```
