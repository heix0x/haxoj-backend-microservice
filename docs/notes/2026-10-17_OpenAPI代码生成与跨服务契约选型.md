# OpenAPI 代码生成（client / server stub）与跨服务契约选型

> 这份笔记单独讲「跨服务契约的第三种解法」——**以 OpenAPI 描述文件为事实来源，各端生成 stub**。
>
> 关联阅读：
>
> - 《2026-10-17\_Feign声明式服务调用与service-client》—— 讲前两种解法（契约分离、接口共享）和 Feign 原理
> - 《2026-09-09\_API代码生成》—— 本项目**前端**已经落地的 codegen 实录（Knife4j + openapi-typescript-codegen）
>
> 本笔记的重点是**概念与选型**；本项目的**后端服务之间目前没有采用这套方案**，
> 第 7 节的工具链属于「如果要用，长什么样」，均标注为示意，不是既成事实。

***

## 1. 先回到问题：跨服务契约一共有三条路

「A 服务要调用 B 服务，两边怎么保证接口对得上」这件事，业界有三条路：

| 路线         | 一句话概括                              | 事实来源             |
| ---------- | ---------------------------------- | ---------------- |
| ① 契约分离     | 共享模块里放手写接口，提供方另写 Controller 满足路径约定 | 手写 Java 接口       |
| ② 接口共享     | 提供方直接 `implements` 共享接口            | 手写 Java 接口       |
| ③ **代码生成** | **一份 OpenAPI 描述，各端生成自己的 stub**     | **OpenAPI 描述文件** |

前两条在 Feign 笔记里讲透了。这份笔记讲第三条 —— 也是最「工程化」的一条。

***

## 2. 核心思想：把事实来源从「Java 接口」换成「中立的描述文件」

前两条路的事实来源都是**手写的 Java 接口**。代码生成方案换了个源头：

```
                     ┌──────────────────────────────┐
                     │  OpenAPI 描述文件             │
                     │  (YAML / JSON，语言无关)      │
                     │  只描述：路径 / 方法 / 参数 / Schema
                     └──────────────┬───────────────┘
                                    │ 一份描述，多处生成
              ┌─────────────────────┼─────────────────────┐
              ▼                     ▼                     ▼
      消费方 client stub      提供方 server stub      文档 / Mock
      （TS、Java、Python…）   （Java、Go…）          （可视化、联调）6
```

**关键认知：OpenAPI 描述里没有任何框架语义。**
它不写 `@FeignClient`、不写 `@RequestMapping`、不写 `@RequestBody`，它描述的是**HTTP 接口本身**：
「有这么一条 `GET /api/user/inner/get/id`，参数 `userId` 是 query，返回一个 `User` schema」。

> **这正是它比 Feign 接口「中立」的地方**：Feign 接口本质是一份「HTTP 调用说明书」，绑死了 Java 和 Spring 注解；
> OpenAPI 是一份「HTTP 接口描述」，Java、TypeScript、Go 都能读懂并生成代码。
> 「中立」是它能跨语言、能同时解决多端问题的根本原因。

***

## 3. 生成什么：client stub 与 server stub

「client / server stub」指的是同一份描述**分别给两端生成产物**：

| 生成物             | 给谁  | 生成出来是什么                | 本项目对应物                   |
| --------------- | --- | ---------------------- | ------------------------ |
| **client stub** | 消费方 | HTTP 客户端代码：一个方法 = 一次请求 | 前端 `src/api/services/*`  |
| **server stub** | 提供方 | 服务端骨架：接口 / 委托类，提供方去实现它 | 后端暂未使用                   |
| **models**      | 双方  | DTO / 类型定义             | 前端 `src/api/models/*.ts` |
| **文档 / Mock**   | 联调  | 可视化文档、可交互 Mock 服务      | Knife4j 文档页              |

**注意 server stub 的价值**：它生成一份**由契约文件推导出来的接口**，提供方 `implements` 它。
这样既拿到了「② 接口共享」的编译期校验，又**不需要手写共享接口**，从而绕开了 ② 的两条代价（契约焊死、Bean 冲突）。

> 也就是说：**代码生成是「想要编译期校验，又不想付耦合代价」的答案。**

***

## 4. 为什么它同时有「解耦」和「编译期校验」

这是它比前两条路都成熟的地方，三句话讲透：

1. **解耦**：生成物是**产物**，不是共享源码。消费方依赖生成的 client，提供方依赖生成的 server，
   两边**没有共享的 Java 类型**，只在「生成那一刻」由同一份 OpenAPI 对齐。
2. **编译期校验**：契约变了 → 重新生成 → 两边重新编译 → **谁对不上谁编译不过**。
3. **中立 / 跨语言**：同一份 OpenAPI 能同时产出 TypeScript（前端）、Java（后端）、Go（某服务），
   而前两条路的 Java 接口只能服务 Java 端。

一句话：

> **一份描述，各自生成，各自编译，对不上编译不过。**

这是它和「手写接口共享」最本质的区别 —— 后者也能编译期校验，但代价是两边被同一份源码绑死。

## 5. 本项目已落地的部分：前端

**后端服务间没用，但前端已经在用了。** 这是标准流水线：

```
后端 Knife4j 暴露文档                          前端构建期
GET /api/v2/api-docs?group=default  ──api:download──▶ api-docs.json
                                                          │
                                              openapi --client axios
                                                          ▼
                                                    src/api（client + models）
                                                          │
                                                  postprocess-api.cjs
                                                          ▼
                                            修补 BASE / WITH_CREDENTIALS
```

对应的 `package.json` 脚本：

```json
"api:download": "curl -s -o api-docs.json \"http://localhost:8101/api/v2/api-docs?group=default\"",
"api:generate": "npm run api:download && openapi --input api-docs.json --output src/api --client axios --useOptions && node scripts/postprocess-api.cjs"
```

`openapi-typescript-codegen` 生成 axios 版 client，产物落在 `src/api`。

> **这段流水线本身就是 codegen 方案代价的活证据**：生成器输出的 `BASE` 硬编码、`WITH_CREDENTIALS` 默认 `false`，
> 不符合项目需要，所以不得不写 `scripts/postprocess-api.cjs` 做后置修补。
> **「模板未必贴合你的场景」是 codegen 最典型的成本。**（详见《2026-09-09\_API代码生成》）

## 6. 如果要把 codegen 用到「服务之间」（示意，本项目未采用）

Java 侧的标准工具链是两件套。

### 6.1 产出 OpenAPI：springdoc-openapi

它扫描 Controller 注解，自动生成 OpenAPI 3 文档（默认 `GET /v3/api-docs`）。

> 本项目当前用的是 **Knife4j**（`knife4j.enable: true`），暴露 Swagger 2 格式的
> `/api/v2/api-docs?group=default` —— 前端脚本拉的就是它。springdoc 是更现代的 OpenAPI 3 替代品，定位相同。

### 6.2 从 OpenAPI 生成代码：openapi-generator-maven-plugin

```xml
<!-- 示意：本项目并未使用 -->
<plugin>
  <groupId>org.openapitools</groupId>
  <artifactId>openapi-generator-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals><goal>generate</goal></goals>
      <configuration>
        <inputSpec>${project.basedir}/src/main/resources/inner-api.yaml</inputSpec>
        <generatorName>java</generatorName>
        <library>feign</library>   <!-- 生成 Feign client：既有契约保证，又有 Nacos/LoadBalancer -->
        <apiPackage>com.hax.haxojbackend.client</apiPackage>
        <modelPackage>com.hax.haxojbackend.model</modelPackage>
      </configuration>
    </execution>
  </executions>
</plugin>
```

| `generatorName`                            | 生成什么                         | 用途                                  |
| ------------------------------------------ | ---------------------------- | ----------------------------------- |
| `java` + `<library>feign</library>`        | **Feign client**             | 消费方：保留 Feign 运行时能力（Nacos 选址、负载均衡）   |
| `java` + `<library>resttemplate</library>` | RestTemplate 客户端             | 消费方（不依赖 Feign）                      |
| `spring`                                   | **server stub**（delegate 模式） | 提供方：`implements` 生成的委托接口            |
| `typescript-axios`                         | 前端 client                    | 可替换现有的 `openapi-typescript-codegen` |

### 6.3 服务间落地时的关键治理点（容易漏）

一个服务的 OpenAPI 会包含**对外公开接口**（`/api/user/login` 等），
但跨服务调用**只需要 inner 那部分**。所以必须做「契约裁剪」，两种做法：

1. 给 inner 接口**单独开一个 group**（Knife4j / springdoc 都支持按 group 暴露）；
2. 单独维护一份 `inner-api.yaml`，只写跨服务那十来个接口。

> 这是 codegen 方案引入的**额外治理成本** —— 前两条路（手写接口）天然就没有这个问题，
> 因为 service-client 里写的就是「只有跨服务才用的那部分」。

## 7. 代价与坑（诚实清单）

| 坑                   | 说明                                          |
| ------------------- | ------------------------------------------- |
| **构建期链路变复杂**        | 契约文件 → 生成 → 编译，CI 里必须跑这一步；漏跑或忘了跑，编译直接失败     |
| **生成物「入库 or 产物」两难** | 入库便于 diff 但要防人肉手改；当产物则每次构建生成。两种流派都有争议       |
| **模板未必贴合**          | 本项目前端就得靠 `postprocess-api.cjs` 修补 —— 铁证     |
| **文档质量决定生成质量**      | 注解 / schema 写得不完整，生成物就退化（类型丢失、具体对象变成 `Map`） |
| **生成器升级引发大 diff**   | 换个生成器版本，所有生成物可能一起变，review 成本高               |
| **对小契约可能过重**        | 只有 3 个方法的内网接口，专门维护 yaml + 插件，收益可能不抵成本       |
| **生成代码难调试**         | 可读性尚可，但断点 / 排查不如手写代码直观                      |
| **需要额外裁剪契约**        | 见 6.3：得把「对外接口」和「跨服务接口」分开治理                  |

**这正好解释了本项目为什么「分叉选型」：**

- **前端**用 codegen —— 接口多、面向多端、形态稳定 → 收益大
- **服务间 service-client** 用手写契约 —— 只有十来个方法、单一 Java 语言、快速迭代 → codegen 过重

> **选型不是「哪个技术更高级」，而是「哪个成本收益比更合适」。**
> 同一套系统里，前端用 codegen、后端手写契约，是完全合理的。

## 8. 三方案终极对比（从「事实来源」维度）

| 维度        | ① 契约分离（本项目服务间）             | ② 接口共享（provider implements）   | ③ **OpenAPI 代码生成**       |
| --------- | -------------------------- | ----------------------------- | ------------------------ |
| **事实来源**  | 手写 Java 接口（service-client） | 手写 Java 接口（双方共用）              | **OpenAPI 描述文件**         |
| **消费方产物** | 手写接口 + Feign 代理            | 手写接口 + Feign 代理               | **生成的 client stub**      |
| **提供方产物** | 手写 Controller 满足约定         | 手写 Controller `implements` 接口 | **生成的 server stub**      |
| **一致性保障** | ❌ 运行时才暴露                   | ✅ 编译期                         | ✅ **编译期**                |
| **语言绑定**  | Java only                  | Java only                     | **跨语言**（TS / Java / Go…） |
| **耦合度**   | 低                          | 高（契约焊死）                       | **低**（只有生成物依赖描述）         |
| **主要成本**  | 写错不报错，靠测试兜底                | Bean 冲突、契约演进受限                | **构建链路 + 契约治理**          |
| **本项目用法** | ✅ 服务间在用                    | ❌ 未用                          | ⚠️ **仅前端在用**             |
| **适合场景**  | 少量内网接口、快速迭代                | 服务少、消费方固定                     | 接口多、多语言、对外公开、契约先行        |

***

## 9. 什么时候该选它

**适合：**

- 接口数量多，且**需要多语言客户端**（前端 TS + 后端 + 外部开放平台）
- 契约要**对第三方公开**（OpenAPI 本身就是给外部看的文档）
- 团队规模大，走 **contract-first（契约先行）** 开发：先定义 `yaml`，再生成两端骨架
- 已有 CI，能承受「生成 → 编译」这条链路

**不适合：**

- 内部就几个接口、单一语言、还在快速迭代（**就是本项目服务间目前的状态**）
- 团队没有 CI 习惯，生成物靠手动执行 → 极易出现「两边生成时间不同步」的隐性不一致

***

## 10. 一句话总结

> **代码生成 = 把「事实来源」从手写的 Java 接口，换成一份语言无关的 OpenAPI 描述；
> 两端各自生成 stub、各自参与编译，从而同时拿到「解耦」和「编译期校验」。**
> 代价是多了一条构建链路和一份契约治理成本 ——
> 所以它更适合「**接口多、跨语言、要对外**」的场合，而不是几个内网接口。
