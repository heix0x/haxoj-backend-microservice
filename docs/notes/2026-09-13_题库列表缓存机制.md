# 题库列表缓存机制实现笔记

> 日期：2026-09-13
> 项目：haxoj 前端
> 涉及文件：
> - `src/utils/questionListCache.ts`（缓存模块，本次新增）
> - `src/views/Problems.vue`（题库列表页，读缓存 + 手动刷新）
> - `src/views/ProblemDetail.vue`（做题页，提交成功后作废缓存）
> - `src/views/ManageQuestion.vue`（题目管理页，删除成功后作废缓存）
> - `src/views/CreateQuestion.vue`（新增/编辑题目成功后作废缓存）

---

## 1. 为什么要做缓存

题库列表页（`/problems`）的数据来自脱敏接口 `POST /api/question/list/page/vo`。

没有缓存时的重复请求场景：

1. 打开题库看到第 1 页 → 请求 A
2. 点"做题"进入做题页
3. 返回题库 → 组件重新创建、`onMounted` 重新触发 → **再次请求完全相同的 A**
4. 翻到第 2 页又翻回来 → **第三次请求 A**

题目列表是低频变化数据，短时间内重复拉取相同分页纯属浪费：增加后端压力、
页面反复闪 loading、浪费流量。

**缓存目标：相同查询条件 + 数据仍然"新鲜"时，直接复用上一次响应，不发请求。**

---

## 2. 设计选型：cache-aside（旁路缓存）+ TTL + 主动失效

最终采用的是三件套组合：

| 手段 | 解决什么问题 |
|---|---|
| 读时先查缓存（cache-aside） | 翻页、页面来回切换不重复请求 |
| TTL（2 分钟） | 兜底"其他用户导致的数据变化"，数据最多旧 2 分钟 |
| 主动失效（clear） | "我确定数据变了"的操作（自己提交、管理员改题）后立即拿到新数据 |
| 手动刷新按钮 | 用户任何时刻都能强制跳过缓存，不必 F5 |

读取流程（cache-aside 三步走）：

```
加载列表
  ├─ 1. 先查缓存：命中且未过期 → 直接渲染，不发请求
  ├─ 2. 未命中 / 已过期 / 强制刷新 → 调后端接口
  └─ 3. 请求成功 → 回填缓存（失败绝不写缓存！）
```

## 3. 实现细节

### 3.1 缓存容器为什么放在独立模块

最初版本把缓存写在 `Problems.vue` 的 `<script setup>` 里。问题：做题页、题目管理页
是不同的**懒加载 chunk**，它们在"提交代码 / 改题"后无法作废列表页内部的缓存。

最终抽到独立模块 `src/utils/questionListCache.ts`，导出三个函数：

```ts
// 读取（过期自动删除并返回 undefined）
getQuestionListCache<T>(key)
// 写入（过期时间 = 当前时间 + TTL）
setQuestionListCache<T>(key, data, total)
// 作废全部列表缓存
clearQuestionListCache()
```

> ES Module 单例特性：模块只在首次 import 时执行一次，内部的 `Map` 在整个 SPA
> 生命周期内被所有页面共享。

**为什么不用组件内变量 / Pinia / localStorage：**

| 方案 | 不采用的原因 |
|---|---|
| 组件内 `const map = new Map()` | 组件销毁重建后丢失，"返回题库"命中不了 |
| Pinia | Pinia 存"业务状态"；接口响应快照放缓存模块职责更清晰（也不是不能放） |
| localStorage | 会让**跨刷新**也读到旧数据，脏数据残留风险更大；当前只需要"页面切换不重复请求"，内存足够 |
| HTTP 强缓存（304/ETag） | 仍有网络往返，且后端接口是 POST，强缓存不适用 |

### 3.2 key 设计：查询条件指纹

```ts
const buildCacheKey = () =>
  `${searchParams.title}|${searchParams.current}|${searchParams.pageSize}`
```

**所有影响查询结果的条件都必须进 key**。漏一个就会"串数据"
（比如搜 A 却显示 B 的结果、第 1 页显示第 2 页内容）。

示例：`"|1|10"`（无搜索第 1 页）、`"两数之和|2|10"`（搜索结果第 2 页）。

### 3.3 过期策略：存绝对时间点

```ts
interface QuestionListCacheItem<T> {
  data: T
  total: number
  expireAt: number  // 过期时间点（时间戳），不是"剩余存活时长"
}

// 写入
expireAt: Date.now() + CACHE_TTL
// 读取判断
item.expireAt <= Date.now()  // 已过期
```

存绝对时间点只需一次大小比较；存"存活时长"则每次读取都要记录经过时间，更繁琐。

TTL 当前为 **2 分钟**（`2 * 60 * 1000`）。取这个值的原因：
列表中的通过率会随其他用户提交而变化，属于"会被他人改变"的数据，TTL 不宜过长。

### 3.4 强制刷新参数

```ts
const loadData = async (forceRefresh = false) => {
  if (!forceRefresh) {
    const cached = getQuestionListCache(key)
    if (cached) { /* 直接用缓存 */ return }
  }
  // 发请求...
}
```

- 翻页 / 搜索 / `onMounted` → `loadData()`（允许缓存）
- 工具栏「刷新」按钮、错误提示上的「重试」→ `loadData(true)`（绕过缓存）

### 3.5 主动失效的时机

| 触发动作 | 文件 | 理由 |
|---|---|---|
| 用户提交代码成功 | `ProblemDetail.vue` | 该题 submitNum/acceptedNum 变化，列表通过率已过期 |
| 管理员新增题目成功 | `CreateQuestion.vue` | 分页结果可能出现新题 |
| 管理员编辑题目成功 | `CreateQuestion.vue` | 标题/标签等列表字段可能变化 |
| 管理员删除题目成功 | `ManageQuestion.vue` | 分页结果中该题应消失 |

四处都只在 **`res.code === 0`（后端确认成功）之后** 才 `clearQuestionListCache()`，
失败操作不清缓存。

当前是"一把全清"（`cache.clear()`）。列表缓存条数很少（每页一条），全清最简单；
以后若缓存维度增多，可改为按 key 前缀精确失效。

## 4. 踩坑记录 / 关键注意点

1. **失败响应绝不写缓存**。只在 `code === 0` 分支回填。否则后端短暂报错时，
   错误结果会被冻住整个 TTL，用户点重试都拿不到新数据。
2. **F5 刷新天然清缓存**。内存缓存在 JS 重新加载后消失——这反而是安全网：
   任何缓存逻辑出 bug，用户都能用刷新整页恢复。
3. **雪花 ID 与本机制无关但容易混**：缓存 key 不包含题目 id 之外的特殊处理；
   做题页路径 `/problems/:id` 中的 id 全程保持字符串（19 位 Long，转 Number 会精度丢失）。
4. **第一版 TTL 是 5 分钟，太长**。复盘"他人提交导致通过率变化"的场景后缩短到 2 分钟。
   TTL 本质是"数据最多能旧多久"与"请求节省率"之间的权衡，没有万能值。
5. **模块级变量 vs setup 变量**：`<script setup>` 每次组件实例化都会重跑，
   但独立 util 模块只加载一次——需要跨页面/跨实例共享的缓存必须放独立模块。

## 5. 方案边界与后续可选升级

当前实现是"最小够用版"，已知边界：

| 特性 | 现状 | 如需升级 |
|---|---|---|
| 持久化 | 仅内存，F5 即失效 | 需要跨刷新保留时换 sessionStorage/localStorage（注意加版本号与主动清理） |
| 他人数据变化感知 | 靠 2 分钟 TTL + 手动刷新 | `visibilitychange`（切回标签页静默刷新）/ SWR（先显缓存再后台更新） |
| 实时性 | 秒级实时做不到 | WebSocket / SSE 由后端推送变更通知 |
| 容量 | 无上限 | 数据量很小无需处理；缓存维度变多后可加 LRU 淘汰 |
| 并发请求 | 快速连点搜索可能发多个请求 | 可缓存"进行中的 Promise"做请求去重（in-flight dedup） |
| 失效粒度 | 全清 | 改为按查询条件 key 前缀精确失效 |
