> 日期：2026-09-17

---

## 一、为什么会乱码？—— 一个核心原理

乱码的本质只有一句话：**读和写用了不同的编码。**

```
写入方用编码 A 把字符 → 字节
读取方用编码 B 把字节 → 字符
A ≠ B → 乱码
```

只要保证"**谁写的就用谁的编码去读**"，就不会乱码。所有编码问题的排查都从这个原理出发。

## 二、本项目遇到的编码问题

### 2.1 javac 错误信息乱码（ProcessUtils）

**现象**：javac 编译失败时，`errorMessage` 里中文全是乱码：

```
javac: ??Ч?ı??... ?÷?: javac <options> <source files>
```

**排查过程**：

| 尝试 | 结果 | 原因 |
|---|---|---|
| 不指定编码（默认） | 乱码 | Java 默认用系统编码，但 `InputStreamReader` 不传编码时行为不确定 |
| 改成 `UTF_8` | 仍然乱码 | javac 在 Windows 中文系统上输出的是 **GBK**，不是 UTF-8 |
| 改成 `GBK` | ✅ 正常 | 读写编码匹配了 |

**修复**：[ProcessUtils.java](file:///d:/project/yupi/hax-oj/haxoj/haxoj-code-sandbox/src/main/java/com/hax/haxojcodesandbox/utils/ProcessUtils.java) 三处 `InputStreamReader` 都加 `Charset.forName("GBK")`。

**为什么 javac 输出 GBK？** Windows 的控制台程序默认用系统 ANSI 代码页（中文系统是 CP936 = GBK）。javac 是通过 `System.err` 输出错误信息的，走的是操作系统的控制台编码。

**关键教训**：`javac -encoding utf-8` 这个参数只控制**源文件的编码**（告诉 javac 你的 .java 文件是 UTF-8），**不控制错误信息的输出编码**。两者是独立的。

### 2.2 Java 源文件路径中的反斜杠导致 Unicode 转义错误

**现象**：Java 文件头部注释写了 Windows 路径 `D:\project\yupi\...`，编译报 Unicode 转义错误。

**原因**：Java 编译器在词法分析阶段会扫描 `\u` 开头的 Unicode 转义序列。路径中的 `\u`（比如 `\yupi` 里的 `\y` 不触发，但 `\user` 里的 `\u` 会被当作 Unicode 转义开始）。注释里的 `\u` 同样会被解析，不是"注释里就安全"。

**修复**：Java 文件头注释里用正斜杠 `/` 代替反斜杠 `\`。

```java
// ❌ 会报错
// D:\project\yupi\hax-oj\haxoj-backend

// ✅ 安全
// D:/project/yupi/hax-oj/haxoj-backend
```

### 2.3 编译命令指定源文件编码

```java
String compileCmd = String.format("javac -encoding utf-8 %s", userCodeFile.getAbsolutePath());
```

`-encoding utf-8` 告诉 javac：**用户代码文件是 UTF-8 编码的**。因为保存用户代码时用的是 `StandardCharsets.UTF_8`：

```java
File userCodeFile = FileUtil.writeString(code, userCodePath, StandardCharsets.UTF_8);
```

写入用 UTF-8 → 编译时告诉 javac 用 UTF-8 → 一致，不会乱码。

### 2.4 java 程序运行输出乱码（同一方法两种编码）

**现象**：编译乱码修好后，运行用户代码时输出又乱码了：

```
ExecuteMessage(exitValue=0, message=缁撴灉:3, errorMessage=null, time=null)
```

`缁撴灉` 应该是 `结果` 之类的中文。

**根因**：运行命令加了 `-Dfile.encoding=UTF-8`，所以 java 程序的 `System.out` 用 **UTF-8** 输出；但 `ProcessUtils` 统一用 GBK 读取 → 又不匹配了。

```
编译阶段：javac 输出 GBK  → ProcessUtils 用 GBK 读 → ✅
运行阶段：java 输出 UTF-8 → ProcessUtils 用 GBK 读 → ❌ 乱码
```

**同一个 `runProcessAndGetMessage` 方法，两个阶段的输出编码不同**，不能写死一个编码。

**修复**：给方法加 `Charset` 参数，调用方按需传入：

```java
// ProcessUtils —— 新增 charset 参数
public static ExecuteMessage runProcessAndGetMessage(
        Process runProcess, String opName, Charset charset) throws IOException {
    // 内部所有 InputStreamReader 都用传入的 charset
    new InputStreamReader(runProcess.getInputStream(), charset)
    ...
}
```

```java
// JavaNativeCodeSandbox —— 编译用 GBK，运行用 UTF-8
// 编译：javac 在 Windows 中文系统输出 GBK
ProcessUtils.runProcessAndGetMessage(compileProcess, "编译", Charset.forName("GBK"));

// 运行：java -Dfile.encoding=UTF-8，输出是 UTF-8
ProcessUtils.runProcessAndGetMessage(runProcess, "运行", StandardCharsets.UTF_8);
```

**教训**：当一个方法被多个调用方共用、而各调用方的编码不一致时，不能在方法内部写死编码，应该把编码作为参数暴露出去，让调用方自己决定。这和"依赖注入"的思想一致——不要替调用方做决定。

### 2.5 前端 API 请求的编码（axios）

前端用 axios 发请求，JSON body 里的中文不需要特殊处理——axios 默认用 UTF-8 序列化 JSON，后端 Spring 的 `@RequestBody` 默认也用 UTF-8 反序列化。这条链路通常不会出问题，除非有人手动改了 `Content-Type` 的 charset。

## 三、Java 开发必须知道的编码知识点

### 3.1 几个概念分清

| 概念 | 含义 | 例子 |
|---|---|---|
| **字符集（Charset）** | 字符和数字的映射表 | Unicode、GBK、ASCII |
| **编码（Encoding）** | 数字到字节的转换规则 | UTF-8、UTF-16、GBK |
| **代码页（Code Page）** | Windows 对编码的编号 | CP936 = GBK，CP65001 = UTF-8 |

Unicode 是字符集（给每个字符编了个号），UTF-8 是编码规则（规定编号怎么存成字节）。日常说"UTF-8 编码"时，字符集和编码是一起说的。

### 3.2 Java 中常见的编码场景

```
                          Java 程序
                              │
     ┌────────────────────────┼────────────────────────┐
     │                        │                        │
  读文件                    读写进程                 HTTP 请求/响应
     │                        │                        │
  FileReader              InputStreamReader          @RequestBody
  InputStream             Process.getInputStream()   @ResponseBody
  -encoding               -encoding
     │                        │                        │
  必须指定编码！           必须指定编码！            Spring 默认 UTF-8
```

**规则：凡是涉及"字节 → 字符"转换的地方，都要显式指定编码，不要依赖默认值。**

### 3.3 不传编码时 Java 用什么？

| 场景 | 默认编码 | 怎么查 |
|---|---|---|
| `new InputStreamReader(stream)` | `Charset.defaultCharset()` | 取决于 JVM 启动参数和系统 |
| `new String(bytes)` | 同上 | 同上 |
| `String.getBytes()` | 同上 | 同上 |
| `FileReader`（Java 11 前） | 同上 | Java 11+ 可传 Charset |
| Spring `@RequestBody` | UTF-8 | Spring Boot 默认配置 |

`Charset.defaultCharset()` 在 Windows 中文系统上通常是 GBK，在 Linux/Mac 上通常是 UTF-8。**这就是同一份代码换台机器就乱码的原因**——默认值随系统变。

### 3.4 读取进程输出的正确写法

```java
// ❌ 不指定编码——跨平台行为不一致
new BufferedReader(new InputStreamReader(process.getInputStream()))

// ❌ 硬编码 UTF-8——在 Windows 上读 GBK 输出会乱码
new BufferedReader(new InputStreamReader(process.getInputStream(), StandardCharsets.UTF_8))

// ✅ 和被调用程序的输出编码保持一致
// Windows 中文系统的 javac/java 输出是 GBK
new BufferedReader(new InputStreamReader(process.getInputStream(), Charset.forName("GBK")))
```

> 进阶：更健壮的做法是在启动进程时通过环境变量指定输出编码：
> ```java
> ProcessBuilder pb = new ProcessBuilder("javac", ...);
> pb.environment().put("JAVA_TOOL_OPTIONS", "-Dfile.encoding=UTF-8 -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8");
> ```
> Java 18+ 还可以用 `-Dstdout.encoding` 和 `-Dstderr.encoding` 直接控制。

### 3.5 Windows 的三层编码

Windows 上容易乱码，是因为存在三层编码可能不一致：

```
程序输出编码（javac: GBK）
    ↓
控制台编码（cmd: CP936/GBK，PowerShell: 可能是 UTF-8）
    ↓
Java 读取编码（InputStreamReader: 你指定的）
```

三层都一致才不乱码。本项目里 Java 直接读 javac 的输出流（不经过控制台），所以只需要保证"javac 输出编码"和"Java 读取编码"一致。

### 3.6 项目中各环节的编码对照表

| 环节 | 编码 | 谁负责保证 |
|---|---|---|
| 用户代码文件写入 | UTF-8 | `FileUtil.writeString(code, path, StandardCharsets.UTF_8)` |
| javac 编译读源文件 | UTF-8 | `javac -encoding utf-8` |
| javac 错误信息输出 | GBK（Windows 中文系统） | 操作系统 ANSI 代码页 |
| Java 读取 javac 错误信息 | GBK | `ProcessUtils.runProcessAndGetMessage(..., Charset.forName("GBK"))` |
| java 程序运行输出 | UTF-8 | `java -Dfile.encoding=UTF-8` 启动参数 |
| Java 读取 java 程序输出 | UTF-8 | `ProcessUtils.runProcessAndGetMessage(..., StandardCharsets.UTF_8)` |
| 后端 HTTP 响应 | UTF-8 | Spring Boot 默认 |
| 前端 axios 请求 | UTF-8 | axios 默认 |
| Java 源代码文件本身 | UTF-8 | IDE 设置（IntelliJ 默认 UTF-8） |
| Java 源代码注释中的路径 | 正斜杠 `/` | 避免 `\u` 触发 Unicode 转义 |

## 四、排查乱码的通用方法

遇到乱码时，按这三步排查：

**第一步：确认写入方用的什么编码**

- 文件 → 看保存时的编码设置（IDE 右下角）
- 进程输出 → Windows 上大概率是 GBK，Linux 上大概率是 UTF-8
- HTTP 请求 → 看 `Content-Type` 头里的 `charset=`

**第二步：确认读取方用的什么编码**

- `InputStreamReader` / `FileReader` → 看有没有传 Charset 参数
- 没传 → 查 `Charset.defaultCharset()` 在当前系统是什么

**第三步：让两者一致**

- 写入是 UTF-8 → 读取也用 UTF-8
- 写入是 GBK → 读取也用 GBK
- 能统一成 UTF-8 最好（跨平台安全），不行就按实际情况匹配

---

## 五、一句话总结

> **乱码 = 读写编码不一致。** Java 凡是做"字节↔字符"转换的地方（读文件、读进程输出、new String、getBytes），都要显式指定编码，不要依赖系统默认值。本项目的核心教训：**编译和运行两个阶段的输出编码不同**——javac 错误信息是 GBK（Windows 系统编码），java 程序输出是 UTF-8（因为 `-Dfile.encoding=UTF-8`），所以 `ProcessUtils` 不能写死一个编码，而是通过参数让调用方分别传入 GBK 和 UTF-8。
