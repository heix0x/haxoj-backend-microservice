## 一、要解决的问题：单体 1 个 doc.html，微服务变成 N 个

|              | 单体 `haxoj-backend`               | 拆分后                     |
| ------------ | -------------------------------- | ----------------------- |
| 文档数量         | 1 个                              | 每个业务服务各 1 个             |
| 访问方式         | `http://localhost:8101/doc.html` | 8101 / 8102 / 8103 各开一个 |
| 测试 / 前端同学的体验 | 一次看完                             | 要开 N 个页面，还要记住哪个接口在哪个服务  |

**聚合**就是：把 N 份文档**在网关这一层凑成一份**，对外只暴露一个入口
`http://localhost:8001/doc.html`。这件事之所以要放在网关做，是因为**网关本来就是唯一对外入口**
（见网关笔记），聚合视图放在这里，既符合「唯一入口」的架构，也不用改任何业务服务的代码。

## 二、先懂原理：文档到底是怎么"生成"出来的

不搞清这条流水线，配置只能靠背；懂了之后，很多"玄学 404"都能自己推。

### 2.1 三段流水线

```
① 注解/配置        ② 框架扫描          ③ 暴露 JSON              ④ UI 渲染
Controller 上的     springfox 按        GET /v2/api-docs        doc.html
@Api/@ApiOperation  「包」扫描，构建     （一份 Swagger2 规范     （knife4j 提供的
 + knife4j 的分组     内存中的 API 模型     的 JSON 描述）            增强版 UI）
   配置(api-rule)    (Swagger 资源)
```

- ① 写注解（本项目基本没写，所以文档里没中文描述 —— 这是可以后续补的）
- ② **框架按包扫**：配置项 `api-rule: package` + `api-rule-resources` 就是这一步的开关
- ③ 暴露一个**固定的 JSON 地址**：OpenAPI2（springfox）是 `/v2/api-docs`；OpenAPI3（springdoc）是 `/v3/api-docs`
- ④ `doc.html` 只是个 **UI**，它去读 ③ 的 JSON 渲染出来

> **一句话**：knife4j ≈ 「一个更漂亮的 Swagger UI + 一堆增强配置」；**文档数据本身来自 springfox / springdoc**，不是 knife4j 生成的。

### 2.2 关键推论：文档是「按包扫描」出来的 —— **扫描范围 = 安全边界**

这是本次改造里最值得记的一条**原理级**结论：

> 谁能被扫到，谁就会被公开在文档上。

- 上次我们做 inner 收口，靠的是**路径**（`/api/inner/**` 网关拦掉）；
- 但文档**不看路径**，它看**包**。inner Controller 原来放在 `controller.inner` 子包下，
  而文档配置扫的是 `com.hax.haxojbackend.controller` → **子包会被递归扫到** → inner 会出现在 `/doc.html` 上。
- 路径上拦得住「调不通」，但拦不住「被公开描述」（路径、参数、返回结构全暴露）。

所以本次配套动作是：**把 3 个 inner Controller 从 `controller.inner` 挪到平级的
`com.hax.haxojbackend.inner`**，让包扫描天然扫不到它们。这样「调不通」和「看不到」两条防线才一致。

> 教训：**安全边界要和「生成文档的机制」对齐**，否则会出现「接口调不通，但接口清单已经公开」的错位。

### 2.3 knife4j / springfox / springdoc 三者的关系

| 名字 | 角色 | 栈 |
| --- | --- | --- |
| `knife4j-openapi2-spring-boot-starter` | 提供 UI + 增强配置，**内含 springfox 2.10.5** | Servlet |
| `knife4j-openapi3-spring-boot-starter` | 同上，**内含 springdoc-openapi** | Servlet |
| `knife4j-gateway-spring-boot-starter` | **只做聚合**，不含上面的 UI 依赖 | WebFlux |

## 三、OpenAPI2 与 OpenAPI3 两种规范，本项目为什么选 OpenAPI2

| | **OpenAPI2（Swagger2）** | **OpenAPI3** |
| --- | --- | --- |
| 底层实现 | **springfox**（knife4j 4.x 锁在 2.10.5） | **springdoc-openapi** |
| 文档地址 | `/v2/api-docs` | `/v3/api-docs` |
| 注解 | `@Api` / `@ApiOperation` | `@Tag` / `@Operation` |
| 现状 | 停更很久 | 活跃 |

**选 OpenAPI2 的三条理由**：

1. **和单体一致**：单体 `haxoj-backend` 用的就是 `knife4j-openapi2-spring-boot-starter` **4.4.0**，
   迁移时不引入第二种规范，注解/配置都能直接沿用。
2. **Spring Boot 版本**：本微服务是 2.6.13。knife4j 4.x 的分支里，
   「Spring Boot 2」这一支官方支持范围是 **2.4.0 ~ 3.0.0**，2.6.13 在范围内，直接用。
   （OpenAPI3 那一支也没问题，但换规范要重写注解，收益为零。）
3. **聚合时两个版本不能混**：`discover.version` 必须与**所有子服务**一致（`swagger2` | `openapi3`），
   一旦统一，配置里就只能写一个值。

## 四、原理核心：网关聚合时，knife4j 怎么知道「每个服务在网关上的前缀」？

聚合要能工作，knife4j 必须回答两个问题：

1. **有哪些子服务**？（从 `DiscoveryClient`，也就是 **Nacos** 拿）
2. **每个服务的文档，在网关这一层该用什么路径去取**？（← 真正容易出错的地方）

第 2 个问题就是「前缀」。knife4j 判断前缀有**三个数据源**，按顺序/组合使用：

| # | 数据源 | 何时生效 | 长什么样 |
| --- | --- | --- | --- |
| ① | `knife4j.gateway.routes`（`strategy: manual`） | 手动模式 | `url: /user/v2/api-docs?group=default`（**网关相对路径，要算上网关前缀**） |
| ② | `DiscoveryClientRouteDefinitionLocator` | 只有 `spring.cloud.gateway.discovery.locator.enabled: true` 时 | 按服务名自动生成 `Path=/{serviceId}/**` |
| ③ | **开发者自己写的 `spring.cloud.gateway.routes`** | 一直都在 | 读路由里的 `Path` 断言，取前缀当作服务前缀 |

> **本项目的处境**：用的是 ③ —— 我们自己的路由是 `Path=/api/user/**`、`Path=/api/question/**`。
> 也就是说，knife4j 拿到的前缀是 **`/api/user`、`/api/question`**（不是服务名）。

### 4.1 聚合取的地址 = 「路由前缀 + `/v2/api-docs`」，与 context-path 撞车（本项目必踩）

先把四个事实摆在一起看：

1. 业务服务都配了 `server.servlet.context-path: /api` → 文档真实端点是 **`/api/v2/api-docs`**
2. 我们自己的网关路由是 `Path=/api/user/**`、`Path=/api/question/**`
3. knife4j（`discover`）取地址的方式是：**「这条路由 Path 的前缀」+ 框架默认的 `/v2/api-docs?group=default`**
   —— 于是它去请求 `http://localhost:8001/api/question/v2/api-docs?group=default`
4. 该请求被网关 `Path=/api/question/**` 路由**正常转发**到 question-service；
   下游剥掉 `context-path=/api` 后是 `/question/v2/api-docs` → **这个端点不存在 → 404**
   （实测：直连 `8102/api/question/v2/api-docs` 与经网关 `8001/...` 返回**逐字相同**的 404 JSON
    → 证明 404 是 **question-service 自己给的**，请求已经正确路由到下游）

⇒ 不改任何东西，一定 404。

**关键澄清（本次翻车点）**：官方文档说「OpenAPI2 可以用 `swagger2.url` 覆盖文档地址」，
但 **knife4j 4.4.0 的 discover 分支根本没有读取这个配置**。
反编译 `knife4j-gateway-spring-boot-starter-4.4.0.jar` 可见：

- `ServiceUtils.getOpenAPIURL(...)` 里是**硬编码**的 `"/v2/api-docs?group=default"`（不读配置）；
- `Knife4jGatewayProperties$Discover.getUrl()`（本该返回 `swagger2.url`）在 4.4.0 里**没有任何调用方**。

所以 `swagger2.url: /api/v2/api-docs?group=default` 是**死配置，天然不生效** ——
这也是为什么"配置看着没错，但地址依然是 `/api/question/v2/api-docs`"。

**真正的修法**（本次采用）：既然 knife4j 拼出的地址一定是 `<路由前缀>/v2/api-docs`，
就**在网关路由上把它重写到下游真实端点**，而不是去改 knife4j：

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: question-service
          uri: lb://haxoj-backend-question-service
          predicates: [Path=/api/question/**,/api/question_submit/**]
          filters:
            # 只对「取文档」这一种请求生效；普通业务请求正则不匹配 → 路径原样不变
            - RewritePath=/api/(question|question_submit)/v2/api-docs, /api/v2/api-docs
```

结果：`/api/question/v2/api-docs?group=default` →（重写）→ 转发到 question-service 时路径已是
`/api/v2/api-docs?group=default` → **200**。

> 记住这条**原理级**判断：**"聚合不上"的 90% 是「knife4j 拼出的地址」与「下游真实地址」对不上**。
> 对不上的根因永远是同一个：
> `<网关路由前缀>` + `<框架默认文档路径>` ≠ `<下游 context-path>` + `<框架默认文档路径>`。
> **修哪里？优先修路由（加 `RewritePath`），不要指望 knife4j 的 `swagger2.url`。**

### 4.2 `discover` 只聚合 `default` 分组

`strategy: discover` 只认每个服务的 **default 分组**。本项目的子服务配置里
`group.default` 就是按这个约定起的名字，正好对上。
如果以后想聚合别的分组，只能在 `discover.routes` 里手动补 —— 这是官方明确写死的限制。

## 五、落地配置

### 5.1 依赖（版本统一收口在父 pom）

父工程 `haxoj-backend-microservice/pom.xml`：

```xml
<properties>
    <!-- 单体用的就是 openapi2（底层 springfox，产出 Swagger2 规范） -->
    <knife4j.version>4.4.0</knife4j.version>

<dependencyManagement>
    <dependencies>
        <!-- 放在 Spring 生态 BOM 之前，和其它第三方依赖一致 -->
        <dependency>
            <groupId>com.github.xiaoymin</groupId>
            <artifactId>knife4j-openapi2-spring-boot-starter</artifactId>
            <version>${knife4j.version}</version>
        </dependency>
        <dependency>
            <groupId>com.github.xiaoymin</groupId>

            <version>${knife4j.version}</version>
        </dependency>
    </dependencies>

```

> 符合项目既有约定：**子模块只声明"要什么"，版本由父工程统一管**。

### 5.2 业务服务（user-service / question-service）

**pom**：加 `knife4j-openapi2-spring-boot-starter`（不写版本）。
> 拆分时漏掉了这个依赖 —— 子服务的 `application.yml` 早就写了 knife4j 配置，
> 但没引 starter，等于配置是"悬空"的，`/api/doc.html` 根本打不开。本次补上。

**yml**：这段之前就有，本次只是它终于生效了：

```yaml
knife4j:
  enable: true
  openapi:
    title: "接口文档"
    version: 1.0
    group:
      default:
        api-rule: package
        api-rule-resources:
          - com.hax.haxojbackend.controller      # ← 扫这个包的"全部子包"
```

### 5.3 网关

**pom**：加 `knife4j-gateway-spring-boot-starter`。
> ⚠️ **只能引这一个**。不要引 `knife4j-openapi2`（springfox 是 Servlet 栈），
> 否则会把 Spring MVC 的自动配置带进 WebFlux 网关，启动就冲突。原因见 §六。

**yml**：

```yaml
knife4j:
  gateway:
    enabled: true                  # 总开关；生产环境务必置 false
    strategy: discover             # 从 Nacos 自动发现子服务，服务上下线文档自动跟随
    discover:
      enabled: true
      version: swagger2            # 子服务统一是 Swagger2 规范
      excluded-services:           # 必须排除网关自身；同时排除只有 inner 的 judge
        - haxoj-backend-gateway
        - haxoj-backend-judge-service
      # ⚠️ 这里刻意不写 swagger2.url：4.4.0 的 discover 分支压根不读它（见 §4.1）
```

**两个配置项各自的"为什么"**：

| 配置 | 不写的后果 |
| --- | --- |
| `excluded-services` 含网关自身 | 网关会去拉自己的文档（它没有），报错或生成空分组 |
| `excluded-services` 含 judge-service | judge 只有 inner 接口，聚合进来等于把内部接口摆上对外文档 |

> 地址对不上（context-path 撞车）这件事**不在这里修**，而在**路由**里加 `RewritePath` —— 见 §5.5 与 §4.1。

### 5.4 配套的安全动作：inner 移包

3 个 inner Controller 从 `controller.inner` 移到 `com.hax.haxojbackend.inner`：

| 服务 | 原路径 | 新路径 |
| --- | --- | --- |
| user | `controller/inner/UserInnerController.java` | `inner/UserInnerController.java` |
| question | `controller/inner/QuestionInnerController.java` | `inner/QuestionInnerController.java` |
| judge | `controller/inner/JudgeInnerController.java` | `inner/JudgeInnerController.java` |

`@RequestMapping` 不变（仍是 `/inner/user`、`/inner/question`、`/inner/judge`），
**只改包名**，所以 Feign 契约、网关路由、拦截规则【全部不用动】。

理由见 §2.2：让「路径拦得住」和「文档扫不到」两条防线对齐。

## 六、为什么网关只能用「WebFlux 版」starter —— 依赖放置的边界

这是本次另一条**原理级**结论：**Servlet 栈和 Reactive 栈不能混**。

| 模块 | 栈 | 能引什么 |
| --- | --- | --- |
| user / question / judge | **Servlet**（`spring-boot-starter-web`，Tomcat） | `knife4j-openapi2`（springfox，Servlet 栈）✅ |
| **gateway** | **Reactive**（`spring-boot-starter-webflux`，Netty） | `knife4j-gateway`（WebFlux 版）✅；springfox ❌ |

两条推论：

1. 网关一旦被塞入 springfox，Spring MVC 的自动配置会进来，和 WebFlux 抢 Servlet 容器 → 启动冲突。
   （网关 pom 里那句「切勿再引入 `spring-boot-starter-web`」是同一个道理。）
2. **因此文档相关依赖/配置不能放进 `common` 模块** —— 因为 `common` 被网关依赖，
   放进去等于间接把 springfox 塞给网关。**"共享模块"的边界 = 谁依赖它，谁就要能承受它的技术栈。**

## 八、踩坑清单

1. **聚合地址 `404` 的头号原因**（§4.1）：knife4j 拼出的地址是
   `<网关路由前缀>` + `/v2/api-docs`，而下游真实地址是 `<context-path>` + `/v2/api-docs`。
   本项目路由前缀是 `/api/user`、`/api/question`，下游 context-path 是 `/api` → 对不上。
   **修法是给路由加 `RewritePath`，不是配 `swagger2.url`。**
2. **`swagger2.url` 在 4.4.0 里是死配置**（§4.1）：`ServiceUtils.getOpenAPIURL(...)` 硬编码，
   `Discover.getUrl()` 无调用方 —— 写了也不生效，别在这上面耗时。
3. **网关自身没排除 → 报错/空分组**（§5.3）。
4. **`discover` 只认 `default` 分组**（§4.2），其它分组只能手动配 `routes`。
5. **两个栈的 starter 不能混**（§六）。
6. **`excluded-services` 里的名字必须与 `spring.application.name` 完全一致**。
7. **服务端 Springfox 与 Spring Boot 2.6+**：需要
   `spring.mvc.pathmatch.matching-strategy: ant_path_matcher`（项目 yml 里已有），
   否则 springfox 会因为默认改用 `PathPatternParser` 而报错。
8. **生产环境必须 `knife4j.gateway.enabled: false`**：聚合页 = 全量接口清单，
   开着等于把内部接口地图挂到公网。官方原文也是这么建议的。
9. **排错口诀**：聚合页空白时，先看浏览器 XHR/Network 里失败的那条 `.../v2/api-docs?group=default`：
   - 它是**哪个前缀**？（= 网关哪条路由的 Path 前缀）
   - 直连该服务同路径是否也 404？（若相同 → 404 由下游给出，说明是"地址对不上"而非"路由没生效"）
