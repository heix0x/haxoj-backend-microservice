## 0. 先看全局：判题到底在做什么

OJ 判题本质只有三件事：

```
① 把不可信的用户代码，放进一个可控环境里跑起来
② 把题目预设的测试输入喂进去，拿到实际输出
③ 拿实际输出和标准答案比对 + 检查时间/内存，给出结论
```

**最重要的一句话**：沙箱**只负责执行，不判断对错**。它返回的是"程序输出了什么"，而不是"答案对不对"。
所有"对/错/超时/超内存"的结论，全部由判题服务（judge-service）的策略层给出。

### 端到端一张图


### 谁负责什么（职责边界是整条链路最重要的一条线）

| 环节 | 代码落点 | 只做 | 明确不做 |
|---|---|---|---|
| 提交 | `QuestionSubmitServiceImpl#doQuestionSubmit` | 校验、落库、计数、发消息 | 不判题、不等结果 |
| 调度 | `JudgeMessageConsumer#onJudgeMessage` | 把消息变成一次判题；决定 ack / 死信 | 不写判题逻辑 |
| 编排 | `JudgeServiceImpl#doJudge` | 状态流转、调沙箱、调策略、回写 | 不执行代码、不比字符串 |
| 执行 | `haxoj-code-sandbox` | 编译、运行、收集 stdout / time / memory | **不判断对错**（`judgeInfo.message` 留空） |
| 判定 | `AbstractJudgeStrategy` | 比对输出、判资源超限、给结论 | 不知道沙箱怎么跑 |
| 落定 | `QuestionSubmitServiceImpl#finishQuestionSubmit` | 状态 + 通过数同事务 | 不信任调用方传的 questionId |

## 1. 数据契约：四个模型撑起整条链路

判题链路上所有模块之间的通信，只靠下面几个 Java 类。**读懂它们 = 读懂判题。**

### 1.1 `ExecuteCodeRequest` —— 把什么交给沙箱

```java
public class ExecuteCodeRequest {
    private String code;             // 用户提交的源代码
    private String language;         // "java"（当前只支持 java，其它语言在提交入口已拦截）
    private List<String> inputList;  // 每个测试用例的输入，一个元素 = 一次运行
}
```

### 1.2 `ExecuteCodeResponse` —— 沙箱还回来什么

```java
public class ExecuteCodeResponse {
    private List<String> outputList;  // 每个用例的实际输出，下标与 inputList 一一对应
    private String message;           // 出错时的信息（编译错误、运行错误、超时文案）
    private Integer status;           // 见下表
    private JudgeInfo judgeInfo;      // 耗时、内存等原始指标（message 留空，由后端填）
}
```

`status` 三种取值（前后端都按这个认）：

| 值 | 含义 | 谁的问题 |
|---|---|---|
| 1 | 正常跑完，`outputList` 里是答案 | — |
| 2 | 沙箱自身出错（编译环境炸了、拉不到镜像、语言不支持） | 平台 → 重试/找管理员 |
| 3 | 用户代码有问题（编译不过、运行报错、超时） | 答题人 → 改代码 |

> ⚠️ 这里的 `status` 与数据库 `QuestionSubmit.status`（0/1/2/3 提交状态）**完全是两套东西**，数值巧合部分重叠，读代码时别混。

### 1.3 `ExecuteMessage` —— 沙箱内部的"进程级"中间产物

```java
public class ExecuteMessage {
    private Integer exitValue;    // 进程退出码，0 = 成功
    private String message;       // 标准输出（stdout）
    private String errorMessage;  // 标准错误（stderr）
    private Long time;            // 本次耗时（ms）
    private Long memory;          // 本次峰值内存（字节，Docker stats 采集）
}
```

对应关系：**N 个 `ExecuteMessage` → 聚合 → 1 个 `ExecuteCodeResponse`**。

### 1.4 `JudgeInfo` —— 判题指标 + 最终结论

```java
public class JudgeInfo {
    private String message;  // 最终结论，由后端策略层写入；沙箱侧留空
    private Long memory;     // KB（沙箱侧已做 字节→KB 换算）
    private Long time;       // ms
}
```

### 1.5 结论枚举 `JudgeInfoMessageEnum`

| 枚举 | 值（存库/传输） | 中文 | 当前是否会被赋值 |
|---|---|---|---|
| `ACCEPTED` | `Accepted` | 成功 | ✅ |
| `WRONG_ANSWER` | `Wrong Answer` | 答案错误 | ✅ |
| `COMPILE_ERROR` | `Compile Error` | 编译错误 | ✅（status=3 且非超时文案） |
| `MEMORY_LIMIT_EXCEEDED` | `Memory Limit Exceeded` | 内存溢出 | ✅ |
| `TIME_LIMIT_EXCEEDED` | `Time Limit Exceeded` | 超时 | ✅（沙箱超时文案匹配） |
| `SYSTEM_ERROR` | `System Error` | 系统错误 | ✅（status=2、无用例、消费兜底） |
| `RUNTIME_ERROR` | `Runtime Error` | 运行错误 | ❌ 沙箱 status=3 把它和编译错误混在一起 |
| 其余（`PRESENTATION_ERROR` 等） | — | — | ❌ 预留坑位 |

### 1.6 契约维护的代价

两端是**两份独立的类**（judge-service 侧在 `judge/codesandbox/model`，沙箱侧在 `model`），只有字段名一致。
任何一边改字段名/类型，另一边都会**静默解析成 null**。改动时务必两边同步。

## 2. 提交入口：落库 → 计数 → 发消息

`QuestionSubmitServiceImpl#doQuestionSubmit`（question-service）只有四步，顺序不能换：

```java
// ① 校验：questionId > 0、语言枚举合法、题目存在、用户已登录
//    枚举里有 java / c++ / golang，但沙箱只实现 java → 这里显式拦截
if (languageEnum != QuestionSubmitLanguageEnum.JAVA) {
    throw new BusinessException(ErrorCode.PARAMS_ERROR, "当前仅支持 Java 提交");
}

// ② 落库：状态置为待判题
questionSubmit.setStatus(QuestionSubmitStatusEnum.WAITING.getValue());   // 0
this.save(questionSubmit);

// ③ 提交数 +1（读出来 +1 再写回，靠 synchronized(this) 兜底 → 技术债，见第 9 节）
questionService.updateById(updateQuestion);

// ④ 投递判题消息，消息体只有 { questionSubmitId, timestamp }
judgeMessageProducer.sendJudgeMessage(questionSubmit.getId());
return questionSubmit.getId();
```

三个判断值得记住：

- **为什么先落库再发消息**：判题是异步的，落库是这条提交存在的唯一凭据。消息里只带 id，消费方回查最新数据——消息永远不会"过期"。
- **为什么只带 id（薄消息）**：代码可能很大、题目可能改过；带快照会让"消息里的数据"和"库里的数据"分叉。薄消息的代价是消费时要多一次 Feign。
- **为什么非 Java 在入口拦**：沙箱对非 java 返回 `status=2`（平台故障语义），判题侧会判成「系统错误」，用户会等一个不会来的修复。拦在入口，用户看到的是「当前仅支持 Java 提交」。

> 已知窗口：落库成功、发消息失败 → 提交永远停在 WAITING（见第 9 节 #4）。

## 3. 队列与消费：一条消息的三种结局

### 3.1 拓扑

```
haxoj.judge.exchange (direct)
  └─ judge.submit ──▶ haxoj.judge.queue (durable, prefetch=1)
                          │ x-dead-letter-exchange: haxoj.judge.dlx
                          │ x-dead-letter-routing-key: judge.dlq
                          ▼
                     haxoj.judge.dlx ──▶ haxoj.judge.dlq
```

常量集中在 `common/constant/MqConstants`：生产方和消费方共用一份，避免"改一处忘一处 → 消息发出去没人收"。
两个服务各自声明拓扑（`RabbitMqConfig`），声明是幂等的：谁先启动谁创建。

### 3.2 三种结局

`JudgeMessageConsumer#onJudgeMessage` 是 `@RabbitListener(ackMode = "MANUAL")`，**必须自己 ack**：

| 结局 | 触发 | 动作 |
|---|---|---|
| 成功 | `doJudge` 正常返回 | `basicAck` |
| 业务异常 | `BusinessException`（提交/题目不存在、状态不允许） | `markFailed` 落定为 `FAILED + System Error`，再 `basicAck` |
| 系统异常 | 其余 `Exception`（沙箱 500、Feign 超时） | `resetToWaiting` → `basicNack(requeue=false)` → DLQ |

两个容易做错的点：

1. **业务异常不能只 ack**：异常可能发生在 claim 成功之后（状态已是 RUNNING），消息一 ack 就再没人管这条提交，前端永远转圈。落定用的是带 `WHERE status=RUNNING` 守卫的 finish，所以不会把一条已成功的提交改坏。
2. **不能 `requeue=true`**：同一条消息会立刻回到队头，形成死循环，把消费者 CPU 打满。进死信，等人工/定时重放。

## 4. 判题主流程：`JudgeServiceImpl#doJudge`

```java
// ① 数据都在 question-service，这里全部走 Feign
QuestionSubmit questionSubmit = questionFeignClient.getQuestionSubmitById(id);
Question question = questionFeignClient.getQuestionById(questionSubmit.getQuestionId());

// ② 幂等短路：重复消息、已判过的直接跳过（省掉后面所有远程调用）
if (!WAITING.getValue().equals(questionSubmit.getStatus())) return questionSubmit;

// ③ 原子抢占：只有改成功的那一个消费者能继续
if (!questionFeignClient.claimQuestionSubmit(id)) return questionSubmit;

// ④ 工厂 + 代理（代理只打日志，不改行为）
CodeSandbox codeSandbox = new CodeSandboxProxy(CodeSandboxFactory.newInstance(type));  // type 来自 codesandbox.type

// ⑤ 用例输入从题目 JSON 里抽
List<JudgeCase> judgeCaseList = JSONUtil.toList(question.getJudgeCase(), JudgeCase.class);
executeCodeRequest.setInputList(judgeCaseList.stream().map(JudgeCase::getInput)
        .collect(Collectors.toList()));

// ⑥ 调沙箱；沙箱不可用会抛 SystemException → 消费者走死信
ExecuteCodeResponse response = codeSandbox.executeCode(executeCodeRequest);

// ⑦ 先按沙箱 status 分流，再决定进不进策略
if (response.getStatus() != 1) judgeInfo = buildFailureJudgeInfo(response);
else judgeInfo = new JudgeManager().doJudge(judgeContext);

// ⑧ 单事务落定；false = 状态既非"判题中"也非终态 → 抛系统异常重试
if (!questionFeignClient.finishQuestionSubmit(finishRequest)) {
    throw new SystemException(ErrorCode.OPERATION_ERROR, "提交状态落定失败");
}
```

**⑦ 是关键**：`status != 1` 时 `outputList` 是空的，交给策略层只会命中"输出条数 ≠ 用例条数" → 判成「答案错误」。
用户拿着「答案错误」去改算法，实际该补的是 `import`。所以这里先定性：

| 沙箱 status | message 特征 | 定性 |
|---|---|---|
| `2` | — | `System Error`（平台故障，跟用户代码无关） |
| `3` | 含「执行超时」 | `Time Limit Exceeded` |
| `3` | 其余 | `Compile Error` |

> status=3 在协议里把「编译失败 / 运行异常 / 超时」混成了一个值，所以只能靠文案匹配。
> 要精确区分 `Runtime Error` 得扩协议——已登记为遗留（第 9 节 #1）。

## 5. 沙箱主干

### 5.1 入口与选型：`SandboxController#executeCode`

先做三件事：`auth` 头比对 `MD5("secretKey")`（失败 403）、语言校验（非 java 直接 `status=2`）、选实现。

选实现的优先级（**两个维度不要混**）：

```
请求参数 ?type=  ──有──▶ 以参数为准（仅本地调试）
      │ 无
      ▼
sandbox.type 配置 ──▶ 服务端部署决定（生产 docker）
      │ 缺失
      ▼
代码兜底 docker
```

| 词 | 出现在哪 | 回答的问题 |
|---|---|---|
| `example` / `remote` / `third party` | 后端 `codesandbox.type` | 用**哪个沙箱服务** |
| `docker` / `native` | 沙箱服务内部 `sandbox.type` | **那个服务里**怎么隔离 |

`native`（零隔离）不能由外部请求随意降级——把它钉死在服务端部署配置里，生产路径就不可能被外部改掉。

### 5.2 模板方法五步：`JavaCodeSandboxTemplate#executeCode`

| 步 | 方法 | 关键点 |
|---|---|---|
| 1 | `saveCodeToFile` | `tmpCode/<UUID>/Main.java`；UUID 隔离并发；写文件强制 UTF-8 |
| 2 | `compileCode` | `javac -encoding utf-8`；**错误流用 GBK 读**（Windows 中文系统 javac 输出编码）；两个编码管的是两件独立的事 |
| 3 | `runFile`（抽象） | Docker：建容器 → 每用例 exec → 删容器；Native：直接 `java -cp` |
| 4 | `collectOutput` | 有 stderr → `status=3` 并 break；输出 `trimEnd`；取 max(time)、max(memory) |
| 5 | `deleteFile` | 在 `finally` 里删整个 UUID 目录（早退路径也不漏） |

**第 2 步的提前返回**：`compileCode` 的 `exitValue != 0` 直接 `return buildErrorResponse(msg, 3)`，不起容器。
这一条把「编译错误」和「运行错误」在沙箱侧就分开了（虽然都返回 3）。

**第 4 步的两个细节**：

```java
// ① println 的换行必须去掉：stdout 是 "3\n"，题目配的是 "3"，equals 逐字符比较不相等
outputList.add(output == null ? null : StrUtil.trimEnd(output));

// ② 内存单位换算在沙箱完成：Docker 采到的是字节，题目 memoryLimit 是 KB
judgeInfo.setMemory(maxMemory / 1024);
```

`trimEnd` 而不是 `trim`：只去末尾，行内换行属于答案本身；同时能把 Windows 的 `\r\n` 一起收掉。
放在模板里而不是某个具体沙箱里：docker / native / 以后接的第三方沙箱自动都生效。

### 5.3 Docker 实现：六步与四道锁

```
① createDockerClient()            连 dockerd
② ensureImage()                   本地没有才 pull（幂等）
③ createAndStartContainer()       -v <宿主目录>:/app，四道锁，start
④ 每个用例 executeOneCase()       容器只建一次，exec 跑多次
⑤ finally removeContainer(force)  不管成败都删
```

四道锁：

| 锁 | 参数 | 挡住什么 |
|---|---|---|
| 内存 | `withMemory(100MB)` + `withMemorySwap(100MB)` | 吃光内存；swap 设 0 会滑到硬盘慢慢跑，永远等不到超时 |
| CPU | `withCpuCount(1)` | 死循环占满所有核 |
| 网络 | `withNetworkDisabled(true)` | 下载东西、连内网 |
| 文件系统 | `withReadonlyRootfs(true)` + 只挂载 `/app` | 改容器系统文件、写别处 |

**输入为什么"双通道"**：`printf '%s\n' '<input>' | java -cp /app Main '<a>' '<b>'`。
`Scanner(System.in)` 从 stdin 读、`main(String[])` 从参数读，两种写法都得能跑。
只用参数的话，写 Scanner 的代码 stdin 永远空着 → 阻塞 → 5 秒超时，看起来像"代码太慢"。

> 容器只建一次、用例跑多次：建容器贵，exec 便宜。

### 5.4 ⭐ 沙箱回调在哪（Docker 实现的三个回调）

都在 `JavaDockerCodeSandbox#executeOneCase`（拉镜像那个在 `ensureImage`），全部来自 docker-java 的流式 API。

**① 执行结果回调（最主要的那一个）**——`ExecStartResultCallback`：

```java
ExecStartResultCallback callback = new ExecStartResultCallback() {
    @Override
    public void onComplete() {          // 流正常结束 = 没超时
        finished[0] = true;
        super.onComplete();
    }

    @Override
    public void onNext(Frame frame) {   // 每来一帧输出就调一次
        String text = new String(frame.getPayload(), StandardCharsets.UTF_8);
        if (StreamType.STDERR.equals(frame.getStreamType())) {
            errorMessage.append(text);  // 追加，不是赋值
        } else {
            message.append(text);
        }
        super.onNext(frame);
    }
};
dockerClient.execStartCmd(execId).exec(callback)
        .awaitCompletion(TIME_OUT, TimeUnit.MILLISECONDS);   // 5000ms 后不再等
```

- `onNext` 必须 `append`：一次输出可能分成很多帧推过来（内存日志那种一行一行刷），覆盖只能拿到最后一帧。
- `onComplete` 没被调用 = 超时 → 事后补 `errorMessage = "执行超时：超过 5000 毫秒"`，这条文案就是第 4 节 TLE 定性的匹配依据。
- `awaitCompletion(5000ms)` 到点只是"不再等"，**容器里的进程还在跑**；真正的兜底是 `finally` 里的 `removeContainer(force)`。
- `message` / `errorMessage` / `finished` 用长度 1 的数组：匿名内部类只能捕获 effectively final 的局部变量，数组变量本身不变、元素可改。

**② 内存采样回调**——`ResultCallback.Adapter<Statistics>`：

```java
StatsCmd statsCmd = dockerClient.statsCmd(containerId);      // 必须在 execStart 之前订阅
statsCmd.exec(new ResultCallback.Adapter<Statistics>() {
    @Override
    public void onNext(Statistics statistics) {
        Long usage = statistics.getMemoryStats().getUsage();  // 字节
        if (usage != null) maxMemory[0] = Math.max(maxMemory[0], usage);
    }
});
```

`statsCmd` 是持续推送的，exec 结束后必须 `close()`，否则回调线程一直挂着。

**③ 拉镜像进度回调**——`PullImageResultCallback#onNext(PullResponseItem)`：
只在本地没有镜像时触发，靠 `awaitCompletion()` 等它把进度推完——少了这句主线程会立刻往下走，镜像其实还在下。

> **Native 路径没有回调**：`JavaNativeCodeSandbox1#runFile` 走 `ProcessUtils#runProcessAndGetMessage`，
> 是 `waitFor()` + `readLine()` 的同步阻塞读。三个后果：没有超时（死循环会一直等）、
> 成功分支不读 stderr、输入只拼在命令行参数上（不喂 stdin）。
> 所以 native 只适合本地对照调试，生产固定 docker。

### 5.5 超时链路串起来

```
awaitCompletion 5s 超时 → onComplete 未调用 → errorMessage = "执行超时：超过 5000 毫秒"
  → collectOutput 看到非空 errorMessage → status=3
  → judge-service buildFailureJudgeInfo 匹配「执行超时」→ TIME_LIMIT_EXCEEDED
```

整条超时链路靠这一句文案串起来——这是当前协议最脆弱的一环（第 9 节 #1、#5）。

## 6. 策略层：对错到底怎么判

`AbstractJudgeStrategy#doJudge` 是模板方法，子类只回答一个问题：这门语言给多少启动宽限。

**判定顺序是刻意的：内存 → 时间 → 用例数 → 逐项内容。**

```java
// ① 内存（KB 对 KB，不换算）
if (memory > memoryLimit) → Memory Limit Exceeded

// ② 时间（ms 对 ms）
if (time > timeLimit + timeAllowanceMs()) → Time Limit Exceeded

// ③ 没有用例的题目不能放行：否则 0 == 0 会让任何代码都 AC
if (judgeCaseList.isEmpty()) → System Error

// ④ 输出条数不等 → Wrong Answer
// ⑤ 逐项 Objects.equals（预期输出可能是 null，不能直接调 equals）
```

为什么先判资源：被超时掐断、被 OOM 杀掉的程序输出必然不完整。先比输出会判成「答案错误」，用户去改算法，而实际该降复杂度。**资源超限是更接近事实的结论。**

空值语义统一为「未设置限制即不判」：

| 情况 | 处理 |
|---|---|
| `judgeConfig` 为空 / 解析失败 | 跳过资源判定，只比输出（DEBUG 日志） |
| `memoryLimit` / `timeLimit` 为 null | 跳过该项 |
| 沙箱没采到 time / memory | 按 0 参与比较 |
| 预期输出为 null | `Objects.equals` |

宽限：

| 策略 | 宽限 | 判定式 |
|---|---|---|
| `DefaultJudgeStrategy` | 0 | `time > timeLimit` |
| `JavaLanguageJudgeStrategy` | 1000ms | `time > timeLimit + 1000` |

宽限只覆盖"算法还没开始跑"的固定开销（JVM 启动、docker exec），不是给慢算法开后门。
**它必须小于沙箱的执行上限（5000ms）**，否则「超时」这个结论会从词典里消失——早期那个 10s 常量就是这么失效的。

## 7. 落定：状态与通过数同生同死

`QuestionSubmitServiceImpl#finishQuestionSubmit`（`@Transactional`）：

```
① 只接受终态（2 / 3），否则 PARAMS_ERROR —— 不许把状态机往回拨
② 已是终态 → return true（幂等命中，重复消息到此为止）
③ 条件更新：UPDATE ... SET status=?, judgeInfo=? WHERE id=? AND status=RUNNING
④ 0 行 → 回读一次：已是终态 = 并发下被别人落定（正常，return true）；否则 return false
⑤ 本次真的推进到 SUCCEED 才 acceptedNum = acceptedNum + 1
⑥ +1 失败 → 抛异常整笔回滚（宁可等下次重试，也不留"状态成功、通过数没加"）
```

返回值只回答一件事：**要不要重试**（`true` = 消息可以 ack；`false` = 抛系统异常走死信）。

为什么不用 `updateById`：它按主键更新，没有状态守卫。`update(wrapper)` 才能表达"只有还在判题中，才允许落定"。
**状态机的守卫要写在 SQL 里，不能写在 Java 的 if 里**——Java 里的检查和更新之间永远有窗口。

## 8. 设计思想（每条锚定到代码落点）

| 思想 | 代码落点 | 为什么 |
|---|---|---|
| **执行与判定分离** | 沙箱返回 `status` + `outputList`；结论由策略写 | 沙箱不可信、不可复用判题口径；换执行引擎（docker/native/第三方）不动判题逻辑 |
| **状态机守卫下沉到 SQL** | `claimQuestionSubmit` / `finishQuestionSubmit` 的 `WHERE status=...` | Java 里 check-then-act 必有窗口；SQL 的条件更新是原子的 |
| **一次远程调用 = 一个事务边界** | `finish` 合并"写状态 + 通过数 +1" | 两次调用中间断一次，重试就会让 +1 幂等地错（多加一次，静默失真） |
| **薄消息** | `JudgeMessage { id, timestamp }` | 消费时回查最新数据，消息不会"过期"；代价是一次 Feign |
| **模板方法** | `JavaCodeSandboxTemplate` 固定 1/2/4/5，只留 `runFile` | 编译、清理、输出整理是共性；只有"在哪跑/怎么跑"该变 |
| **失败分类决定 ack 语义** | 业务异常 ack、系统异常 nack | 重试无意义的要丢弃（防毒消息），重试有意义的要重放（DLQ） |
| **可插拔放在两个维度** | 后端 `codesandbox.type`（选服务）× 沙箱 `sandbox.type`（选隔离方式） | 混成一个字段会让工厂随沙箱实现膨胀；且 native 不能由外部请求降级 |

## 9. 遗留问题清单（按影响排序）

| # | 现状 | 影响 | 方向 |
|---|---|---|---|
| 1 | 沙箱 `status=3` 混着编译失败 / 运行异常 / 超时 | 只能按文案归为 CE，`Runtime Error` 判不出来；超时判定依赖一句中文文案 | 扩协议（加 errorType） |

| 12 | 前端只有提交动作，没有结果页/轮询 | 用户提交后看不到结论 | 补提交记录页 |

## 11. 附录：与单体阶段（2026-09-17 初版）的差异要点

| 单体阶段旧版说 | 现在的事实 |
|---|---|
| `CompletableFuture.runAsync` 异步判题 | RabbitMQ 异步（本笔记 §3） |
| 判题逻辑在 `haxoj-backend/judge` | 独立 `haxoj-backend-judge-service`（8103，无对外 Controller） |
| `haxoj-code-sandbox` 没有任何 Controller | `SandboxController`，`POST /sandbox/execute`，MD5 鉴权 |
| `codesandbox.type: example` 假沙箱 | `type: remote`，真实调用虚拟机 Docker 沙箱 |
| 编译错误会被误判为答案错误 | 沙箱编译失败返回 `status=3`，judge 侧定性为 `Compile Error` |
| Java 宽限 10 秒、永远判不出超时 | 宽限 1000ms，且判定顺序改为「内存 → 时间 → 条数 → 内容」 |
| 内存 null 会 NPE | 空值统一按「未设置限制即不判」；沙箱用 docker stats 采内存 |
| 写状态、通过数 +1 是两次调用 | 合并为单事务 `finishQuestionSubmit`，带 `WHERE status=RUNNING` 守卫 |
| 防重复只靠 Java 里的 if | `claim` 用 `UPDATE ... WHERE status=WAITING` 原子抢占 |
| SecurityManager / 黑名单（WordTree）是安全主线 | 主线改为 Docker 四道锁；SecurityManager 相关类仍在但未接入（native 调试用） |
