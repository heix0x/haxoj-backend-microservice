## 一、本次范围：路由 + 跨域 + 内部接口收口

```
第 1 步（本次）：路由 + 跨域 + inner 不对外，鉴权仍留在各服务
第 2 步（以后）：网关加「登录粗校验」（白名单 + 凭证检查）
第 3 步（更后）：网关解析身份，向下游传用户 ID，服务侧改成读 header
```

**只做第 1 步是有意的**：入口不统一，后面的鉴权、限流、灰度都无从谈起。第 1 步把「入口唯一」先落地，风险最小。

**inner 收口必须和网关一起做**：上网关的那一刻，`Path=/api/user/**` 这类对外路由会**第一次**把 `/inner` 顺手包进开放范围（见第八节）。
以前"没上网关"和"上网关"的暴露面是一样的——一旦上网关，这一步不做就是新开的洞。

## 二、端口规划（本次已决策）

### 1. 决策

| 角色 | 端口 | 对外还是对内 |
| --- | --- | --- |
| **Gateway（网关）** | **8001** | ✅ **唯一对外** |
| user-service | 8101 | ❌ 只对内 |
| question-service | 8102 | ❌ 只对内 |
| judge-service | 8103 | ❌ 只对内（且只有 inner 接口） |
| MySQL / Redis / Nacos | 3306 / 6379 / 8848 | 基础设施 |
| 代码沙箱 **＋** Sentinel 控制台 | 8080 | 独立程序（**两个都占，勿用**） |

### 2. 为什么是 8001，而不是 8104 / 8101

**端口号本质上在编码「信任边界」**：它标记谁能访问它。所以真正的问题是——**要不要让"唯一对外的那个端口"一眼可辨。**

考虑过的四个方案：

| 方案 | 端口 | 迁移成本 | 结论 |
| --- | --- | --- | --- |
| A | 网关 8104，业务不动 | 0 | 只改前端一行，但**不体现入口优先**，网关与业务混在同一段 |
| **B（采用）** | **网关 8001，业务不动** | **0** | ✅ **入口独占 80xx 段，业务留在 81xx 段——段位就分出了对外/对内**，且满足「xxx1」的命名直觉 |
| C | 网关 8100，业务不动 | 0 | 零迁移，但对外/对内分段不如 B 明显 |
| D | 网关 8101，服务后移 8102/8103/8104 | **最大** | 完全对齐鱼皮教程，但三个服务端口都要动，收益只是「跟教程一致」 |

**选 B 的理由**：对外一段、对内一段，比「段内谁排第一」更有运维价值 ——
以后看一眼端口就知道哪些该开防火墙、哪些绝不该暴露。

> 注：`8001` 实测空闲；`8080` 虽然现在也空闲，但被**代码沙箱**和 **Sentinel 控制台**同时预定，**不要用**。

### 3. 「改端口会影响什么」—— 完整清单

| 受影响的点                   | 是否受影响       | 说明                                                     |
| ----------------------- | ----------- | ------------------------------------------------------ |
| 本服务 yml 的 `server.port` | ✅ 必改        | 唯一真正的代码改动（本次业务服务**不改**）                                |
| Nacos 注册的实例地址           | ⚠️ **自动更新** | 服务名不变；Feign 走 `lb://服务名` 而非 IP:端口 → **调用方零改动**         |
| 其他服务的 Feign 调用          | ❌ **不受影响**  | 微服务的红利：**端口是内部实现细节，不是契约**                              |
| 前端 `.env`               | 只改指向网关那一行   | 上网关后前端只认一个地址，服务端口对它彻底透明                                |
| Cookie / 登录态            | ❌ 不受影响      | Cookie 按 **host** 共享、与端口无关（`localhost` 下 8001~8103 共用） |
| 硬编码引用                   | ✅ 要清扫       | 笔记 / README / Postman 集合 / 注释里的 URL                    |
| 与单体同跑                   | ⚠️          | 单体 `haxoj-backend` 和 user-service **都在 8101**，不能同时启动   |
| 防火墙 / 端口映射 / Docker     | 生产才涉及       | 本地开发不用                                                 |

> **一句话**：**现在改代价最小，窗口只有这一次。** 一旦前端开始只连网关，业务服务端口就彻底变成内部细节；
> 但**网关自己那个端口会成为长期契约**，所以它值得一次挑好。

### 4. 端口的「角色」：配置项，不是契约项

接上网关前后最容易混的一点：**端口在系统里到底扮演什么角色？** 一句话结论：

> **端口是「配置项 / 运维项」，不是「契约项」。**

把「谁在看端口」拆成四层，就清楚了：

| 层面 | 谁在看 | 端口有没有意义 |
| --- | --- | --- |
| 接口契约（Feign 里写什么） | 调用方 | ❌ **无** —— 只写 **服务名 + 路径 + 方法** |
| 服务配置（yml 里写什么） | 服务自己 | ✅ **有** —— `server.port` 必须显式配 |
| 注册发现（Nacos 里存什么） | 所有人 | ✅ **有** —— 注册的实例就是 `IP:端口` |
| 对外调用（前端认什么） | 前端 | ✅ **有，但只有网关那一个** |

#### （1）为什么端口能从「契约」里消失

契约写的是：

```java
@FeignClient(name = "haxoj-backend-user-service", path = "/api/user")
```

端口不在这里。**端口是「实例属性」，不是「接口属性」。** 于是：

> user-service 从 8101 换到任意空闲端口，只要 `spring.application.name` 不变、Nacos 注册成功，
> **所有调用方一行都不用改。**

这就是「微服务红利」的具体形态。但**不是 Nacos 一家做到的**，是三件套分工：

| 组件 | 负责什么 | 碰不碰端口 |
| --- | --- | --- |
| **OpenFeign** | 把 Java 方法调用翻译成 HTTP（用**服务名 + 路径**） | ❌ 不管 |
| **Nacos** | 地址簿：服务名 → 实例 `IP:端口` 列表 | ✅ 存的就是它 |
| **LoadBalancer** | 从地址簿里挑一个实例 | ✅ 用的就是它 |

⚠️ **别把它讲成「Nacos 把端口自动化了」** —— Nacos 从不知道你要调**哪个方法**，它只知道这个服务**有哪些实例在跑**。
端口之所以「消失」，是因为**服务名替它扛了「找谁」这件事**，而不是谁把端口抹掉了。

#### （2）但「没业务价值」≠「不用管」

| 端口仍然重要的场景 | 为什么 |
| --- | --- |
| 进程独占资源 | 冲突就起不来（`8080` 被沙箱 + Sentinel 同时占用就是实例） |
| 直连调试 / 绕网关排错 | 定位问题时必须能直接 `curl 8102`，不绕网关 |
| **信任边界（最重要）** | `8103` 只有 inner 接口，**它不该对外** —— 端口就是这条线的物理体现 |
| 多实例 / 灰度 | 同一服务多副本，靠不同端口（或容器）区分 |
| 防火墙 / 端口映射 / Docker | 生产才涉及，但规划从这里开始 |

#### （3）反向的坑：被抽象的是「端口」，不是「地址」

「端口不用管」这个结论**千万别顺手扩大**：

| 契约要素 | 是否被隐藏 | 写错的后果 |
| --- | --- | --- |
| `server.port` | ✅ 隐藏 | 无感（调用方不关心） |
| `spring.application.name` | ❌ **没隐藏** | 找不到实例（**503**），不是找不到端口 |
| 路径 `path = "/api/user"` | ❌ **没隐藏** | **404** —— 必须与对方的 `context-path` + `@RequestMapping` 拼起来一致 |

> **一句话**：端口的价值从「业务契约」转移到了「**配置与信任边界**」。
> 它没消失，只是换了战场 —— 在这里它直接承担安全含义：**业务端口只对内，是网关之外的另一道门**（见第十二节）。

## 四、依赖：不用改，但要记住两条

**现状**（`haxoj-backend-gateway/pom.xml`）：`spring-cloud-starter-gateway` + `nacos-discovery` + `sentinel` + `sentinel-gateway`。

1. **网关不需要额外补 `loadbalancer`**。
   `spring-cloud-starter-gateway` **3.1.4** 的 pom 里已经带了 `spring-boot-starter-webflux` 和 `spring-cloud-starter-loadbalancer`。
   这和 Feign 不一样（Feign 在 Cloud 2021.x 起**必须**手动补 loadbalancer）。
2. **铁律：网关绝不能依赖 `haxoj-backend-common`，也不能依赖 `model`。**
   `common` 里有 `CorsConfig implements WebMvcConfigurer`，还带着 `spring-boot-starter-web` 和 MyBatis-Plus。
   一旦进 classpath，启动直接失败：

   ```
   Spring MVC found on classpath, which is incompatible with Spring Cloud Gateway.
   ```

   网关也不该认识任何业务实体。

## 五、`application.yml`（可直接用）

删掉 `application.properties` 后，在 `src/main/resources/` 下新建 `application.yml`：

```yaml
server:
  port: 8001                          # 唯一对外端口；8101~8103 留给业务服务，8080 被沙箱/Sentinel 占用

spring:
  application:
    name: haxoj-backend-gateway

  main:
    web-application-type: reactive    # 显式声明：网关必须是 WebFlux 栈

  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        username: nacos
        password: nacos
        namespace: public

    gateway:
      # ── 路由：外部路径 → 服务名 ──────────────────────────────
      # 注意 1：judge-service 没有对外 Controller，这里刻意不开路由（见第七节）
      # 注意 2：下面两条路由都覆盖不到 /api/inner/**，所以 inner 天然不可达（见第八节）
      routes:
        - id: user-service
          uri: lb://haxoj-backend-user-service
          predicates:
            - Path=/api/user/**,/api/file/**

        - id: question-service
          uri: lb://haxoj-backend-question-service
          predicates:
            - Path=/api/question/**,/api/question_submit/**

      # ── 跨域：全系统只此一份 ─────────────────────────────────
      globalcors:
        add-to-simple-url-handler-mapping: true
        cors-configurations:
          '[/**]':
            allowedOriginPatterns: "*"   # 不能写 allowedOrigins: "*"（与 allowCredentials 冲突）
            allowedMethods: "*"
            allowedHeaders: "*"
            allowCredentials: true

      # ── 下游还在加 CORS 头，先靠它去重 ───────────────────────
      default-filters:
        - DedupeResponseHeader=Access-Control-Allow-Origin Access-Control-Allow-Credentials, RETAIN_FIRST

      # ── 超时：不配就没有业务层面的上限 ───────────────────────
      httpclient:
        connect-timeout: 5000        # 毫秒
        response-timeout: 30s        # Duration 写法
```

**路由不生效时**，临时加一段开日志，日志会明确写出 `Route matched: user-service` 或 `No route matched`：

```yaml
logging:
  level:
    org.springframework.cloud.gateway: debug
```

### 与鱼皮示例的三点差异（已核对）

| 项 | 鱼皮示例 | 本方案 | 结论 |
| --- | --- | --- | --- |
| 网关端口 | `8101` | **`8001`** | 他项目里 8101 没人占；本项目被 user-service 占了 |
| judge 路由 | 开了 `/api/judge/**` | **刻意不开** | ⚠️ **否掉他**。本项目 judge-service 只有 `JudgeInnerController`，开路由 = 把「触发判题」暴露到公网 |

## 六、路由对照表（从 Controller 核出来的，不是举例）

| 外部实际请求 | 对应 Controller | 所属服务 | 网关开放？ |
| --- | --- | --- | --- |
| `/api/user/**` | `UserController` | user | ✅ |
| `/api/file/**` | `FileController` | user | ✅ |
| `/api/question/**` | `QuestionController` | question | ✅ |
| `/api/question_submit/**` | `QuestionSubmitController` | question | ✅ |
| `/api/user/inner/**` | `UserInnerController` | user | ⚠️ **能！被 `/api/user/**` 覆盖** |
| `/api/question/inner/**` | `QuestionInnerController` | question | ⚠️ **能！被 `/api/question/**` 覆盖** |
| `/api/judge/inner/**` | `JudgeInnerController` | judge | ❌ 不能（压根没配路由） |

> ⚠️ 这三行是**最容易看错的地方**：**`inner` 不等于「到不了」。**
> `/api/user/inner/get/id` 这个路径**落在 `/api/user/**` 的覆盖范围里**，所以外部经网关**能直接打到**。
> 写 `Path=/api/user/**` 的时候，手是往"用户模块的接口"上指的，但**实际开放范围**把 `/inner` 一起包进去了。
> 修法见**第八节**（本次一并修掉）。

**千万别图省事把 `Path` 写成 `/api/**` 一把梭** —— 那不是把所有请求送错服务，就是把某个服务的 `/inner` 一起暴露出去。

> 这条比配置本身重要：**网关的每一条路由，都是一次「对外开放」的决定。**
> 开之前先问：这个路径，外部真的应该能调吗？

## 七、为什么刻意不给 judge-service 开路由

1. 本项目 judge-service **只有 `JudgeInnerController`**（`controller/` 目录下就这一个文件），没有任何对外 Controller。
2. 它的职责是「被 question-service 通过 Feign 调用，异步执行判题」，属于**内部能力**。
3. 给它开 `/api/judge/**` 路由，等于把「触发判题」这个能力放到公网 —— 判题是 CPU/内存密集型操作，被刷会直接把服务打满。

**什么时候才开**：以后如果给 judge-service 加了面向用户/管理的对外接口（比如查询判题详情），再按那个 Controller 的实际路径加路由。

## 八、内部接口（inner）必须不对外 —— 本次一并修掉

> 📌 **2026-10-21 更新**：本节写的 `InnerPathBlockFilter` 已重命名为 **`GlobalAuthFilter`**，
> 与「统一鉴权入口」合并（鉴权开关 `haxoj.gateway.auth.enabled` 默认 `false`，行为不变：inner 仍 404）。
> 本文保留当时的类名，作为历史记录；逐行拆解见 vault 笔记
> `2026-10-21_网关统一鉴权：GlobalAuthFilter 逐行拆解`。

### 1. 问题：`inner` 现在是被「顺手转发」的

```
Path=/api/user/**,/api/file/**        ← 这条路由声明的"开放范围"
     /api/user/inner/get/id           ← 它落在里面，被顺手覆盖
```

`/api/question/inner/**` 同理。**只有 judge 是安全的**，因为 `/api/judge/**` 压根没配路由（第七节）。

> 根因一句话：**inner 的路径挂在了对外前缀的下面。**
> 不是谁忘了加鉴权，是路径规划时没把「内部」独立成段。

### 2. 为什么 inner 必须免鉴权 —— 于是只能靠「到不了」来保护

| | 对外接口 | inner 接口 |
| --- | --- | --- |
| 访客是 | **人**（浏览器） | **别的服务**（Feign） |
| 身份凭证 | 用户 session（`JSESSIONID`） | **无** —— 服务间调用带不了浏览器 Cookie |
| 靠什么识别身份 | `@AuthCheck` + `getLoginUser(request)` | **网络位置**（只该被内网 / 网关内部到达） |
| 返回值 | `BaseResponse<VO>`，脱敏 | 原始实体 |

所以 inner **不能**套用户鉴权（套了 Feign 就调不通），它的安全**完全依赖「外部到不了」**。
而「外部到不了」不能靠类名里的 `inner` 三个字母 —— 必须由 **① 路由 + ② 网络** 落实。

⚠️ 现状核对（读代码确认，不是推测）：

- 三个 inner Controller **都没有 `@AuthCheck`**；
- 全项目唯一的鉴权入口 `AuthInterceptor` 是 `@Around("@annotation(authCheck)")`，**只拦带注解的方法**，没注解就完全不管；
- 全项目唯一的 `WebMvcConfigurer` 是 `CorsConfig`，**没有任何按路径拦截**；
- `User` 实体的 `userPassword` **没有 `@JsonIgnore`**，会被序列化进 JSON。

→ 结论：**现在没有任何一层在拦 inner。**

### 3. 现在真实暴露的接口（经 8001 可达）

| 端点 | 危害 |
| --- | --- |
| `GET /api/user/inner/get/id?userId=N` | 返回**裸 `User`，含 `userPassword`（BCrypt 哈希）** → 遍历 id 即可批量拉走全站密码哈希 |
| `GET /api/user/inner/get/ids?idList=...` | 批量版，同上 |
| `POST /api/question/inner/question_submit/update` | **写接口**：可篡改任意提交的判题状态/判题信息 → **判题结果造假** |
| `POST /api/question/inner/.../update/accepted_num?questionId=` | 可无限刷题目通过数 |
| `GET /api/question/inner/question_submit/get/id` | 泄漏他人提交记录（含代码） |
| `POST /api/judge/inner/do` | 无路由，**但直连 8103 仍可触发判题** → CPU 密集，可被刷爆 |

> 最后一行说明：**网关不是唯一入口。** 只要业务端口能被直连，网关就只是一道可以绕过的门
> → 第十二节「业务端口只对内」那条必须一起做。

### 4. 修法：① 路径收敛（根治） + ② 网关拦截面（防回潮）

**① 路径收敛 —— 让 inner 脱离对外前缀（改 6 行）**

| 服务 | Controller 改这一行 | Feign 契约改这一行 |
| --- | --- | --- |
| user | `@RequestMapping("/inner/user")` | `path = "/api/inner/user"` |
| question | `@RequestMapping("/inner/question")` | `path = "/api/inner/question"` |
| judge | `@RequestMapping("/inner/judge")` | `path = "/api/inner/judge"` |

（`context-path` 仍是 `/api`；**方法级映射全部不动**：`/get/id`、`/get/ids`、`/question_submit/update`、`/do` …）

改完后 inner 的对外路径变成：

```
/api/inner/user/get/id           ← 不属于任何对外路由 → 网关天然 404
/api/inner/question/get/id
/api/inner/judge/do
```

**网关 yml 一个字都不用改** —— `/api/user/**`、`/api/question/**` 都覆盖不到 `/api/inner/**`。
这就是「从路径上根治」：**不暴露的能力，不靠配置去关，而是让它天然不在开放范围里。**

**② 网关拦截面 —— 防「路由被写宽」的回潮**

收敛之后这个 Filter 看似多余，但它是**绊线**：以后谁把路由写成 `Path=/api/**` 一把梭，inner 又会暴露。
所以它同时挡住**新形状**和**旧形状**：

```java
// haxoj-backend-gateway
// 包必须落在 com.hax.haxojbackendgateway 下，否则 @SpringBootApplication 扫不到
// 建议位置：com.hax.haxojbackendgateway.filter.InnerPathBlockFilter
@Component
public class InnerPathBlockFilter implements GlobalFilter, Ordered {

    /** 新形状（路径收敛后） */
    private static final PathPattern NEW_INNER =
            PathPatternParser.defaultInstance.parse("/api/inner/**");
    /** 旧形状（兜底：万一还有漏改的 inner 挂在对外前缀下） */
    private static final PathPattern OLD_INNER =
            PathPatternParser.defaultInstance.parse("/api/{service}/inner/**");

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        PathContainer path = exchange.getRequest().getPath().pathWithinApplication();
        if (NEW_INNER.matches(path) || OLD_INNER.matches(path)) {
            exchange.getResponse().setStatusCode(HttpStatus.NOT_FOUND);
            return exchange.getResponse().setComplete();   // 关键：短路，绝不转发到下游
        }
        return chain.filter(exchange);
    }

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE;   // 必须早于 NettyRoutingFilter，否则请求已经发出去了
    }
}
```

两个必须记住的细节：

- ⚠️ **`setComplete()` 不能省。** 只 `setStatusCode` 等于「设了状态又继续转发」——下游照常执行，响应状态还会被下游覆盖，等于没拦。
- ⚠️ **别写 `/api/**/inner/**`。** PathPattern 的 `**` **只能出现在末尾**，写在中间会解析失败。
  所以用 `{service}` 这种**单段变量**，或者像上面这样拆成两条 pattern。

**两道防线各管一段 —— 三个 404 分别是谁给的（实测归属）**

| 请求 | 谁给的 404 |
| --- | --- |
| `GET /api/inner/user/get/id`（收敛后的新前缀） | **路由层**：没有任何 `routes` 覆盖它，请求在**路由匹配阶段**就 404 了 |
| `GET /api/user/inner/get/id`（旧形状） | **过滤器层**：它匹配上了 `/api/user/**`，是 `InnerPathBlockFilter` 按旧的兜底 pattern 挡住 |
| `GET /api/judge/inner/do` | **路由层**（judge 压根没配路由，见第七节） |

> ⚠️ 所以"没被 `routes` 定义的路径靠过滤器兜底"这个印象**是不成立的**：
> 结果虽然都是 404，但一个来自路由、一个来自过滤器。
> **`GlobalFilter` 只在"已经匹配到路由"之后才会被组装进过滤器链** ——
> 没路由的请求根本走不到过滤器，在阶段 A 就结束了。
>
> 换句话说，这个 Filter **唯一真正的价值**是：
> **当有人把路由写宽（`Path=/api/**` 一把梭）时，它仍然拦得住 `/inner`。** 平时它是「无路由 → 天然 404」，
> 收敛之后它看起来多余，但它拦的是**另一种故障**。
>
> 机制细节（阶段 A / 阶段 B、`WebFilter` 与 `GlobalFilter` 的差别、为什么用 404 而不是 403、`**` 的位置限制）
> 见 [[API 网关：微服务的唯一入口]] §6.5。

**③ 可选加固（本次不做，见第十二节）**：inner 校验共享密钥 `X-Internal-Token`，Feign 侧用 `RequestInterceptor` 自动带上
—— 防的是「网关被绕过、有人直连端口」。

### 5. 顺手值得做掉的：数据层收口

`UserInnerController.getById` 直接返回裸 `User`，里面带 `userPassword`。两种收口：

- 给 `User.userPassword` 加 `@JsonIgnore`（一步到位，但**改了全局序列化**，先确认没有把 `User` 当入参反序列化的地方）；
- 或者 inner 也返回 VO，只带服务间真正需要的字段。

## 九、三个必踩的坑

### 坑 1：`Path` 必须带 `/api`

```
浏览器请求：       /api/user/get/login
网关匹配：         Path=/api/user/**        ✔
网关转发（原样）： /api/user/get/login
下游 context-path：/api  →  Controller 收到 /user/get/login  ✔
```

下游的 `context-path` 是 `/api`，网关**默认原样转发路径**。写成 `/user/**` 就连不上。

### 坑 2：不能加 `StripPrefix=1`

```
加了 StripPrefix=1：/api/user/get/login  →  /user/get/login
下游 context-path 是 /api，它期望的完整路径是 /api/user/get/login
                 →  收到 /user/get/login，匹配不到 → 404
```

`StripPrefix` 是给「下游没有 context-path」的场景用的。本项目有，**所以别用**。

> 坑 1 和坑 2 是网关 404 的两大来源：**该带没带、不该剥却剥。**

### 坑 3：CORS 头会重复

网关加了一份 `globalcors`，各服务里的 `common/CorsConfig` 也还在加一份 → 响应里出现两个 `Access-Control-Allow-Origin`。
本方案用 `DedupeResponseHeader` 先兜住；等路由与跨域都稳定后，可以再考虑把下游的 `CorsConfig` 去掉。

> **实测补记（2026-10-18 晚）—— 修掉一个真实缺陷：`lb://` 路由全部 503**
>
> 冒烟实测时发现，带 `lb://` 的路由（`/api/user/**`、`/api/question/**`）请求网关一律返回
> **503 `Unable to find instance`**。根因与路由配置、inner 拦截都无关：
>
> - Spring Cloud **2021.x 起 `spring-cloud-starter-gateway` 不再传递 `spring-cloud-starter-loadbalancer`**；
> - 网关 pom 里原来的注释「3.1.4 的 pom 已经带了 loadbalancer」是**错的** —— 实测 fat jar 里没有它；
> - 没有 loadbalancer，`lb://` 就没人负责「按服务名选实例」，于是直接 503。
>
> 修法：网关 pom 显式加 `spring-cloud-starter-loadbalancer`（重建后 jar 内
> `BOOT-INF/lib/spring-cloud-starter-loadbalancer-3.1.5.jar` 已存在）。
>
> **教训**：这和之前 memory 里那条「Spring Cloud 2021.x 的 OpenFeign 必须显式引 loadbalancer」
> 是**同一类问题**——2021.x 把 loadbalancer 从多个 starter 的传递依赖里摘了出去。
> 凡是「服务名/`lb://` 选不到实例」的报错，先查 loadbalancer 在不在。
