## 2. 目录结构

```
haxoj-backend-microservice/
├── README.md              ← 门面：是什么、怎么跑
├── AGENTS.md              ← AI/新人的工作手册（地图、约定、边界、验收）
└── docs/
    ├── README.md          ← 本页：文档索引
    ├── architecture.md    ← 系统地图（模块、端口、数据流、关键设计）
    ├── conventions.md     ← 开发规范（只写工具管不了的判断）
    ├── changelog.md       ← 改造日志（时间倒序，新条目在前；旧结论可就地修正）
    ├── known-issues.md    ← 已知问题与风险（快照，带核对日期）
    ├── roadmap.md         ← 下一步建议（快照，带验收标准）
    ├── adr/               ← 架构决策记录（一条一页，一条一个决策）
    │   ├── 0001-从单体到微服务.md
    │   └── 0002-inner接口不对外.md
    ├── notes/             ← 实现记录（按主题+日期；单一正文，过时就地更新）
    └── anatomy/           ← 功能解剖（极小颗粒度功能讲解，随代码更新）
        ├── README.md      ← 目录命名建议、存放规范与索引
        └── JudgeMessageConsumer.md
```

## 3. 当前状态与计划

三份文档维护方式不同，合起来回答"从哪来、现在如何、往哪去"：

| 文档 | 回答 | 性质 |
|---|---|---|
| [`changelog.md`](changelog.md) | 这个项目一共改了什么、什么时候改的、验证到什么程度 | 时间线，旧结论可就地修正 |
| [`known-issues.md`](known-issues.md) | 现在还有什么问题没解决、严重到什么程度 | 快照，修复后改状态 |
| [`roadmap.md`](roadmap.md) | 接下来先做什么、为什么、做完怎么算完成 | 快照，决策变化时改写 |

> 三份文档用同一套稳定 ID：`known-issues.md` 里的 `SEC-3`、`JUD-4` 这类编号不会因为优先级调整而变，
> `roadmap.md` 按同一套编号排期。**不要另起一套编号**，否则交叉引用会失效。

## 5. 文档维护规则（小团队版）

| 规则 | 说明 |
|---|---|
| **改代码同 PR 改文档** | 行为变了，`architecture.md` / README 一起改；没改就是文档债 |
| **单一正文** | 同一主题只有一处正文。内容过时就地更新或删除，**不保留旧版本、不另起"平行文档"重写一遍**；历史交给 git |
| **anatomy 随代码更新** | 讲解"现在怎么工作"，行为变了同 PR 改；规范见 [`anatomy/README.md`](anatomy/README.md) |
| **changelog 记时间线** | 每次改造追加一节（时间倒序）；旧条目结论有误就地修正并标注核对日期 |
| **问题 ID 稳定** | `known-issues.md` 修好的条目改状态不删；新问题追加新 ID，不复用旧 ID |
| **roadmap 保留否决记录** | 不做的方向写进"已否决与延后"并给出触发条件，防止反复提议 |
| **ADR 一条一决策** | 同一决策不重复开篇；结论变更就地更新并注明原因，保留编号 |
| **architecture 定期校** | 大改后（加模块、改端口、改调用链）必须更新 |
| **规范要短** | `conventions.md` 控制在 2 页内；能工具化的规则不写进去 |
| **不写"正确的废话"** | "代码要优雅"这种话不写；写"Controller 不写业务"这种可执行判断 |

## 6. 这份文档体系是怎么分工的

| 文档 | 回答 | 读者 |
|---|---|---|
| README | 是什么、怎么跑 | 第一次来的人 |
| AGENTS.md | 怎么在这个仓库干活 | AI、新同事 |
| architecture | 系统怎么组织 | 开发、评审 |
| conventions | 代码怎么写 | 写代码的人 |
| ADR | 为什么这么选 | 未来的自己 |
| notes | 这个主题怎么做、现在如何 | 复盘、面试 |
| anatomy | 某个类/机制怎么工作、为什么这么设计 | 改这块代码的人 |
| changelog | 一共改了什么、验证到什么程度 | 接手的人、复盘 |
| known-issues | 现在还剩什么问题 | 排期的人、评审 |
| roadmap | 接下来做什么、怎么算做完 | 排期的人、自己 |

> 文档体系的设计原则见 vault 笔记《项目文档体系：需求、设计、规范、README 与 AGENTS.md》（不在本仓库）。
