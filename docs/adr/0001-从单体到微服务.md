# ADR-0001：从单体拆分为微服务

- **状态**：已采纳
- **日期**：2026-10-15
- **决策人**：项目作者
- **相关**：[架构文档](../architecture.md)、[微服务代码拆分笔记](../notes/2026-10-15_微服务代码拆分与ServiceClient.md)

## 背景

项目最初是一个 Spring Boot 单体（用户 / 题目 / 判题 / 沙箱都在一个应用里）。
拆分前的痛点：

- 判题调沙箱是唯一的外部依赖，但和业务代码混在一起；
- 想实践 Spring Cloud 技术栈（Nacos / Feign / Gateway）；
- 单体代码边界开始模糊（controller 里出现跨模块调用）。

约束：**单人开发、学习性质、没有真实流量与运维团队**。

## 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 保持单体 | 简单、事务方便、部署一次 | 学不到分布式治理；边界继续腐化 |
| B. 模块化单体 | 保留单体简单性，强制模块边界 | 仍然只有一个部署单元，练不到服务发现/调用 |
| C. 拆成微服务 | 真实实践注册发现、远程调用、网关、分布式 Session | 分布式复杂度、共享库、运维成本 |

## 决定

选 **C**，拆成 7 个 Maven 模块：
`common` / `model` / `service-client` / `gateway` / `user-service` / `question-service` / `judge-service`。

拆分依据是**业务能力**（用户、题目、判题），不是技术分层。
沙箱保持独立部署（原本就是独立进程）。

## 后果

**正面**

- 真实踩过：Feign 循环依赖、`lb://` 503（loadbalancer 可选依赖）、网关 WebFlux 与 Session 冲突、inner 接口暴露；
- 具备可讲的技术故事（为什么拆、怎么拆、踩了什么）。

**负面 / 代价**

- 三个服务仍共用一个 MySQL 库（分布式单体风险）；
- 没有 MQ、没有链路追踪、测试很少；
- 单人维护 7 个模块，认知负担明显上升。

## 重新评估条件

出现任意一条，应考虑回到模块化单体或减少服务数量：

1. 目标从"学习"转为"尽快上线"，且没有运维支持；
2. 服务之间必须共享事务/强一致；
3. 维护成本超过收益（改一个功能要动 3 个服务）。

> 结论：**这次拆分是"教学优先"的选择，不是"工程最优"的选择。**
