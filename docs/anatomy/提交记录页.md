# 提交记录页：异步判题结果的前端回流

> 一句话定位：一个**只读列表页**，它自己不产生数据——判题是后端 MQ 异步做的，
> 页面的全部职责是「把数据库里已有的结论，按用户能看懂的方式取回来并持续刷新」。
>
> 颗粒度：单页 + 它依赖的一个工具模块（`utils/submission`）与一个组件能力（`MonacoEditor` 的只读模式）。
> 代码截至 2026-10-30。改造过程见 [`../changelog.md`](../changelog.md) §2，遗留见 [`../known-issues.md`](../known-issues.md) `FEAT-1`。

---

## 0. 全链路一览

```
浏览器访问 /submissions
  │ 路由守卫：meta.access = USER，未登录 → /user/login?redirect=/submissions
  ▼
Submissions.vue
  │ loadData(silent) → QuestionSubmitControllerService.listMyQuestionSubmitVoByPageUsingPost
  │ 请求体 { current, pageSize(≤20), status?, sortField:'createTime', sortOrder:'descend' }
  ▼
网关 :8001 ──Path=/api/question_submit/**──▶ question-service :8102
  │ QuestionSubmitController#listMyQuestionSubmitVOByPage
  │ ① 强制 setUserId(登录用户)  ② size>20 → 40000
  ▼
QuestionSubmitServiceImpl#getQueryWrapper → MyBatis-Plus 分页
  ▼
MySQL question_submit（status 0/1/2/3 + judgeInfo JSON）
  │
  ▼ 返回 Page<QuestionSubmitVO>（含 code / judgeInfo / questionVO）
渲染：状态标签、语言、耗时、内存、提交时间
  │
  ├── 存在 status ∈ {0,1} → 3 秒后 loadData(silent) 再来一次（最多 20 轮）
  └── 点行 → 抽屉：a-descriptions + MonacoEditor(readonly) 显示源码
```

| 环节 | 落点 | 职责 |
|---|---|---|
| 入口 | `router/routes.ts` 的 `submissions` 路由 | 权限声明，菜单由 `HaxHeader` 自动生成 |
| 取数 | `Submissions.vue#loadData` | 组装查询、判业务码、处理空页回退、触发轮询 |
| 接口 | `QuestionSubmitControllerService#listMyQuestionSubmitVoByPageUsingPost` | 生成的客户端，路径 `/api/question_submit/my/list/page` |
| 展示口径 | `utils/submission.ts` | 状态文案/颜色、判题结论中文、KB→MB、ms→ms |
| 详情 | `MonacoEditor.vue` | 只读渲染提交源码，随抽屉关闭销毁 |
| 数据来源（异步） | `JudgeMessageConsumer` → `finishQuestionSubmit` | 判题结果写入数据库，页面只负责读 |

> 关键认知：**页面没有任何"等待判题完成"的能力**。它只能反复问「现在是什么状态」。
> 这一点决定了后面所有的设计（轮询、终态判定、60 秒上限）。

## 1. 代码层面：完整工作链路

### 1.1 一次加载的两个入口

`loadData(silent = false)` 是全页唯一的数据入口，但有两种调用方式：

| 调用方 | 参数 | 行为差异 |
|---|---|---|
| `onMounted`、筛选、翻页、刷新按钮 | `silent = false` | `loading = true`，表格出现 loading 遮罩 |
| 轮询定时器 | `silent = true` | 不动 `loading`，静默替换 `dataList` |

**为什么要区分**：轮询是 3 秒一次的后台动作。如果每次都开 `loading`，表格会每 3 秒闪一次白屏，
用户会以为页面在抽搐。静默刷新只更新数据，视觉上只有状态标签发生变化。

函数开头有一道并发闸门：

```ts
if (loading.value) return
```

它挡的是「用户刚点了刷新，定时器又到点」这种重叠请求——同一个列表页并发拉两次没有意义。

### 1.2 分页：上限是后端定的，不是 UI 定的

后端 `listMyQuestionSubmitVOByPage` 里有硬校验：

```java
ThrowUtils.throwIf(size > 20, ErrorCode.PARAMS_ERROR);
```

所以前端只提供 `[10, 20]` 两档（`a-pagination` 的 `page-size-options`），
不去做「允许选 50，出错再提示」这种把约束暴露给用户的写法。**不可能的选择不应该出现在界面上。**

另外两个与分页相关的细节：

- **空页回退**：`dataList.length === 0 && current > 1` 时把 `current` 减 1 重新加载。
  场景是数据被删（管理员删题、清理测试数据）后，用户停留的页码越界，返回空记录。
  不做回退的话，用户看到的是「一页空白」，但总数其实还有。
- **排序**：固定 `sortField: 'createTime'` + `sortOrder: 'descend'`，最新提交在最前。
  后端的 `CommonConstant.SORT_ORDER_ASC` 是 `"ascend"`，传入 `"descend"` 即降序（与题库页同一写法）。

### 1.3 轮询：单定时器 + 轮数上限 + 状态驱动

```ts
const POLL_INTERVAL = 3000
const POLL_MAX_ROUNDS = 20

const pendingCount = computed(() => dataList.value.filter((item) => isPendingStatus(item.status)).length)

const scheduleNextPoll = () => {
  stopPolling()                                    // 先清，保证同时只有一个定时器
  if (pendingCount.value === 0) return             // 没有中间态就不再问
  if (pollRounds >= POLL_MAX_ROUNDS) return        // 60 秒后放弃
  pollTimer = window.setTimeout(() => {
    pollRounds += 1
    loadData(true)                                 // 静默刷新
  }, POLL_INTERVAL)
}
```

四个约束叠在一起，缺一个都会出问题：

| 机制 | 不写会怎样 |
|---|---|
| `stopPolling()` 先执行 | 定时器叠加，1 次操作变成 N 条请求链 |
| `pendingCount === 0` 就停 | 结果早就出来了，页面还在每 3 秒打接口 |
| `pollRounds` 上限 | 后端异常/消息进死信时，页面永远轮询下去 |
| `onBeforeUnmount(stopPolling)` | 离开页面后定时器仍在跑，对着已卸载的组件写数据 |

此外两处刻意的处理：

- **出错不轮询**：`catch` 分支里 `stopPolling()`。后端挂了还每 3 秒重试，等于自己造压测。
- **用户操作重置计数**：筛选、翻页、手动刷新都调 `resetPolling()`，让新一轮有完整的 60 秒预算。

### 1.4 状态与文案：为什么失败要显示 `judgeInfo.message`

数据库里只有 `status`（0 待判题 / 1 判题中 / 2 成功 / 3 失败），
但「失败」对用户没有信息量——他需要知道是**编译错误**还是**答案错误**还是**超时**。
后者存在 `judgeInfo.message` 里（英文枚举值），因此 `getSubmissionStatusText` 的规则是：

| status | 展示 |
|---|---|
| 0 / 1 | 待判题 / 判题中 |
| 2 | 成功（不展示 `Accepted`，中文界面里一个英文单词很突兀） |
| 3 | `judgeInfo.message` 翻译后的中文（答案错误 / 编译错误 / 超时 / 内存溢出…），缺失时回落「失败」 |

`translateJudgeMessage` 负责英文值→中文的映射，未收录的值原样返回（宁可显示英文，也不显示乱码或空）。
`formatMemoryKb` / `formatDurationMs` 把 0 与 `undefined` 都当「无数据」显示 `-`：
判题中时后端本来就没有耗时和内存，显示 `0KB` 会被误解成「没占内存」。

### 1.5 详情抽屉：让重资源跟着生命周期走

- `a-drawer` 加 `unmount-on-close`：抽屉关闭时销毁内容，`MonacoEditor` 的 `onBeforeUnmount` 才会执行 `editorInstance.dispose()`。
  不加这个属性，抽屉只是隐藏，编辑器实例一直挂在那里，反复开关会累积。
- `MonacoEditor` 新增 `readonly` 属性（默认 `false`），传给 `monaco.editor.create` 的 `readOnly`。
  查看历史提交必须只读——否则用户能在别人的历史代码上敲字，产生一种「改了」的错觉。
- 抽屉内容直接复用列表里的 `record`（接口已返回 `code`），不额外请求详情接口。

### 1.6 两种"没有数据"

| 情况 | 表现 | 处理 |
|---|---|---|
| 请求失败 | `loadError` 非空 | `a-alert` + 重试按钮；表格不渲染，避免同时出现错误和空态 |
| 确实没有提交 | 请求成功、`records` 为空 | 表格自带空态：提示「还没有提交记录」+ 去题库 |

## 2. 抽象思想层面：设计理念

### 2.1 轮询不是落后，是"匹配问题形态"

判题已经用 MQ 解耦，一次判题通常几秒内完成。为这种「秒级、一次性、只在页面停留期间关心」的状态
引入 WebSocket / SSE，代价是三处：服务端要维护连接、网关要支持长连接（当前是 WebFlux 转发）、
断线重连与心跳都要写。收益只是省掉几次 GET。

于是选择最朴素的方案，但把它的成本控制住：**只在有中间态时轮询**（状态驱动，而不是固定心跳），
**有轮数上限**（失败不可能靠等解决），**有生命周期清理**（离开即停）。

### 2.2 约束下沉：UI 不假装能突破后端

`pageSize ≤ 20` 是后端用 `40000` 硬挡的规则。前端两种写法：

- 允许选 50，捕获错误再 `Message.error('太多了')` —— 把后端的限制变成用户的困惑；
- 只提供 10 / 20 —— 用户根本不会问"为什么不能选 50"。

选后者。**凡是数据层已经确定的约束，界面就应该表现为"本来就没有这个选项"。**

### 2.3 口径单一：文案和单位只在一个地方定义

状态映射、判题结论翻译、KB→MB、毫秒格式化，全部集中在 `utils/submission.ts`，
提交记录页、用户中心、做题页共用。

不这么做的后果是具体的：两个页面各写一份 `status === 3 ? '失败' : ...`，
某天有人只改了其中一个，于是同一个提交在列表里显示「编译错误」、在用户中心显示「失败」。
用户会以为是两个不同的东西。

### 2.4 生命周期即资源管理

Monaco 是这一页最重的资源（几 MB 的 JS + 独立 Worker）。它出现在抽屉里，而抽屉是**偶发打开**的。
`unmount-on-close` 把"关闭抽屉"与"销毁编辑器"绑在一起，让资源的存活时间严格等于它被需要的时间。
这是一个通用原则：**重资源不要挂在长期存在的容器上，挂在"确实在展示"的那个节点上。**

### 2.5 只读轮询天然幂等

页面所有请求都是读操作，没有任何乐观更新或本地状态合并。
因此重复请求、乱序返回、用户连续点刷新，都不会产生不一致——最坏情况是多一次请求。
这是选择"轮询 + 全量覆盖 `dataList`"而不是"增量 patch"的根本理由：**简单性换来了不会被并发搞坏。**

## 3. 边界与已知取舍

| 边界 | 说明 | 影响 |
|---|---|---|
| 60 秒后停止轮询 | 20 轮 × 3 秒。消息进死信（`CON-5`：DLQ 无重放工具）时，提交会长期停在「判题中」 | 页面不再自动刷新，用户需手动点刷新；真实原因在后端 |
| 只刷新当前页 | 轮询按当前 `dataList` 判断中间态 | 用户翻到第 3 页时，第 1 页新提交的变化看不到（下次进入会重新拉） |
| 每页最多 20 条 | 后端硬限制 | 想一次看更多只能翻页；要放宽必须改后端校验 |
| 路由 chunk 约 3.9MB | Monaco 被打进该页的懒加载 chunk | 首次进入要下载；已按路由拆分，不影响首页 |
| 无前端缓存 | 每次进入都请求 | 多一次请求，但避免了「看到旧判题结果」这类更难解释的问题 |
| 离开页面即停止 | 不做后台轮询/桌面通知 | 判题完成时用户若已离开，不会收到提醒 |
