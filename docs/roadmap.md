# 下一步建议

> 这份文档回答：**接下来先做什么、为什么是它、做完怎么算完成。**
>
> 性质是**快照**：决策变化时改写本篇，但「已否决与延后」一节保留记录和触发条件，
> 避免同一个方向被反复提议又反复否掉。
>
> 问题的证据与状态见 [known-issues.md](./known-issues.md)（ID 一一对应），已完成的历史见 [changelog.md](./changelog.md)。
> 最后核对：2026-10-27。

## 1. 结论先行

按当前状态，建议顺序是：

1. **止血两条**：日志脱敏（`SEC-1`）+ 提交记录页闭环（`FEAT-1`）。`FEAT-1` 已于 10-30 完成，剩 `SEC-1`。
2. **判题可信度**：容器内存与题目限制对齐（`JUD-4`）、提交数并发（`CON-3`）、运行错误与编译错误分开（`JUD-5`）。约一天。
3. **工程底座**：建表 SQL（`ENG-1`）、API 生成脚本（`ENG-2`）、记忆与笔记补齐（`DOC-1`/`DOC-2`）。约一天。
4. **安全边界**：沙箱密钥外置（`SEC-3`）、跨域收敛（`SEC-2`）、内部接口凭证（`SEC-4`）。需要改部署方式，单独排期。
5. **可观测与容量**：traceId、DLQ 重放（`CON-5`）、压测、本地消息表（`CON-4`）。
6. **结构性改造**：分库（`STR-1`）、网关鉴权落地（`SEC-5`）、多机部署（`ENV-4`）。

排序依据不是「哪个更严重」，而是**投入产出比 × 是否阻塞后续**：

- `SEC-1` 是纯收益：改一个切面，不涉及任何契约或部署。
- `FEAT-1` 是唯一一处「界面承诺了、系统做不到」的地方（见 §2.2），修它不依赖别的改动。
- `JUD-4` 会持续产出错误结论，但它需要动沙箱参数，得和 `JUD-5` 一起验证，所以放第二批。
- 安全三条都需要改部署（环境变量、VM 重启、网关策略），一次排期做完更省事。

## 2. 第 1 步：止血

### 2.1 `SEC-1` 请求日志脱敏

**目标**：日志里不再出现密码、token、完整请求体。

**为什么现在做**：登录接口的参数对象里就带着明文密码，任何能看日志的人（包括日志采集系统）都能拿到。这是当前最容易被利用、修复成本最低的一条。

**做法**：`LogInterceptor` 不再 `StringUtils.join(args, ", ")`，改为只记录参数类型与个数；确需字段级信息时，按字段名黑名单（`password` / `token` / `secret`）打码。`GlobalExceptionHandler` 已有「不把堆栈返回前端」的先例，日志侧沿用同样的判断。

**验收**：登录一次后 `grep -i "userPassword\|123456"` 无命中；日志仍能看出「哪个接口、几个参数、耗时多少」。

**改动面**：`haxoj-backend-common/.../aop/LogInterceptor.java`（约 10 行）。

### 2.2 `FEAT-1` 提交记录页闭环（2026-10-30 已完成）

**交付**：独立页 `/submissions`（需登录）——题目 / 状态 / 语言 / 耗时 / 内存 / 提交时间，服务端分页（pageSize ≤ 20）、状态筛选、判题中每 3 秒自动刷新（上限 60 秒）、点行查看源码与判题详情抽屉。实现与验证记录见 [changelog.md](./changelog.md) §2。

**勘误（2026-10-30）**：本节原写「`QuestionSubmitControllerService` 里没有 `my/list/page` 的方法」，核对后不成立——生成产物里该方法一直存在，路径与字段都和后端对齐，所以本次**没有**执行重新生成，`ENG-2` 保持待办。

**验收**：提交一段死循环代码 → 页面在 5~10 秒内从「判题中」变为「超时」；提交正确代码 → 显示「成功 + 耗时/内存」；刷新页面后数据仍在（来自数据库，不是前端状态）。（运行时验收待后端在线后补做，当前仅构建验证。）

**残留（10-30 下午已消除）**：`User.vue` 的 mock 已替换为真实 `get/login` 数据 + 最近 5 条提交；没有接口支撑的「邮箱」「解题数」直接删除，不编造字段。

## 3. 第 2 步：判题可信度

### 3.1 `JUD-4` 容器内存与题目限制对齐

**问题**：容器硬上限 100MB，题目默认 256MB。用户按 256MB 优化，实际 100MB 就被容器杀掉。

**做法**（两个选项，推荐 A）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A（推荐） | 容器上限抬到明显高于所有题目的值（如 512MB），让判题策略按 `memoryLimit` 判 MLE，容器只做兜底 | 单容器可占用更多内存，需按并发数估算宿主机容量 |
| B | 把题目 `memoryLimit` 通过 `ExecuteCodeRequest` 传给沙箱，动态设置容器上限 | 改两端协议，沙箱与判题服务必须同时升级 |

**验收**：`memoryLimit=262144` 的题目下，`-Xmx200m` 的程序通过，`-Xmx400m` 的程序判「内存溢出」而不是「系统错误」。

### 3.2 `CON-3` 提交数并发

**做法**：`QuestionSubmitServiceImpl` 里把 `synchronized (this)` + 读改写改成 `setSql("submitNum = submitNum + 1")`，与通过数的加法保持同一种写法。

**验收**：两个实例各 50 次并发提交，`submitNum` 精确增加 100；单实例下与改造前结果一致。

### 3.3 `JUD-5` 区分运行错误与编译错误

**问题**：沙箱 `status=3` 同时表示编译失败、运行时异常、超时。判题侧只能靠 message 里是否含「执行超时」区分，其余统一归成「编译错误」。

**做法**：扩展沙箱响应，在 `message` 之外增加一个可枚举的失败类型（如 `errorType: COMPILE_ERROR / RUNTIME_ERROR / TIME_LIMIT`），判题侧按类型映射。属于两端协议变更，与 `JUD-4` 的方案 B 同类，可以合并成一次协议升级。

**验收**：提交数组越界的代码显示「运行错误」，提交缺 import 的代码显示「编译错误」，写死循环显示「超时」。

## 4. 第 3 步：工程底座

### 4.1 `ENG-1` 补齐建表 SQL

**做法**：从现有库导出 `question`、`question_submit` 的结构，放到 `sql/schema.sql`（连同 `user` 表），并注明 `map-underscore-to-camel-case: false` 意味着字段名必须与实体严格一致。

**验收**：空库执行脚本 → 启动四个服务 → 完成一次提交并判题成功。

**为什么排在这里**：它不阻塞当前开发（环境已跑起来），但阻塞所有后来者，也可能在换机器时卡住自己。

### 4.2 `ENG-2` 修 API 生成脚本（2026-10-30 已完成）

**做法（实际）**：直连 8101 / 8102 各拉一份 Swagger，分别生成到临时目录后按文件合并；新增 `/api` 前缀断言。
没有走网关聚合文档——核实后确认 knife4j 网关只按 group 暴露各服务文档，没有合并 spec，且经网关取回的 paths 前缀不确定。

**验收（实际）**：`npm run api:generate` 跑通，合并后 43 models / 4 services；`git status src/api` 的差异只有删除 `Post*`/`WxMp*` 死代码与少量对齐；`type-check` + `build` 通过；把地址指向空端口时脚本退出码 1 并给出提示。

**勘误**：本节原验收写「`git diff src/api` 为空」，不成立——生成器基于当前后端，必然会删掉历史遗留的死接口，差异应为「只删死代码 + 只改本次后端变化」。详见 [changelog.md](./changelog.md) §2「同日追加」。

### 4.3 `DOC-1` / `DOC-2` 补齐记录

- `.workbuddy/memory/MEMORY.md` 更新到当前状态（沙箱已接入、判题已异步、判题口径已修）。
- 补一篇 `notes/2026-10-23_沙箱编译失败与stdin.md`（按 notes 约定是追加，不改旧文件），记录「Scanner 写法超时」的成因与修法。

**验收**：新人只读 `AGENTS.md` + `known-issues.md` + 这两份文件，能说清当前判题链路与最近两次修复。

### 4.4 `ENV-1` 沙箱地址配置化

**目标**：换环境不再改代码重新打包。

**做法**：`RemoteCodeSandbox.SANDBOX_EXECUTE_URL` 与 `AUTH_REQUEST_SECRET` 一并移到 `application.yml`（`codesandbox.url` / `codesandbox.auth-secret`），用 `${SANDBOX_URL:...}` 兜底，与数据库密码的写法一致。

**验收**：改配置后重启 judge-service，不重新 `mvn package` 就能指向另一个沙箱实例。

### 4.5 低优先级清理包

一次性处理 `ENG-3`（`JudgeManager` 的 `@Service` 与 `new` 二选一）、`ENG-4`（judge-service 去掉无用的 MyBatis/MySQL 依赖与 datasource）、`ENG-5`（复用 `DockerConfig` 的 `DockerClient` Bean）、`ENG-8`（删 `DockerTestController` 临时接口）、`JUD-6`（native 沙箱加超时强杀）。

**为什么放在一起**：五项都是"改一两处、不影响行为"的清理，单独立项的沟通成本高于改动本身。

**验收**：`mvn -DskipTests package` 通过；judge-service 启动日志里不再有数据源初始化；native 模式跑 `SleepError.java` 在 5 秒内返回「执行超时」。

### 4.6 `ENG-7` 测试补强

**优先级**（沿用 [`conventions.md`](./conventions.md) §8 的既定顺序，不另起一套）：判题状态流转、权限校验、inner 拦截。

**本次必补的一条**：`finishQuestionSubmit` 的幂等与回滚——重复调用不重复 +1、`+1` 失败时状态回滚。目前它只有代码审查，没有测试（见 [known-issues.md](./known-issues.md) §9）。

**验收**：`mvn -pl haxoj-backend-question-service -am test` 能独立跑通；覆盖「连续两次 finish 只 +1」「模拟 +1 失败后状态仍为判题中」。

## 5. 第 4 步：安全边界

| 项 | 做法 | 验收 |
|---|---|---|
| `SEC-3` 沙箱密钥 | 密钥移到配置（`${SANDBOX_AUTH_SECRET}`），两端读同一环境变量；给 `/sandbox/native`、`/sandbox/docker` 加同款校验 | 源码中不再出现该字符串；不带 `auth` 头调 `/sandbox/execute` 返回 403 |
| `SEC-2` 跨域 | 只放行 `http://localhost:5173` 与正式域名；`allowCredentials` 保留但来源收敛 | 用其它 Origin 发预检被拒；本地开发与部署环境不受影响 |
| `SEC-4` 内部凭证 | 网关在下发 inner 路径前直接 404（已有），再加一层 `X-Internal-Token` 校验：Feign 拦截器统一加头，`InnerController` 统一校验 | 不带 token 直连 `127.0.0.1:8101/api/inner/**` 返回 403 |
| `SEC-5` 网关鉴权 | 接响应式 Session 或 JWT，逐个核对白名单后再打开 `haxoj.gateway.auth.enabled` | 打开开关后，未登录访问 `/api/question/list/page/vo` 返回 401，登录后正常 |

> `SEC-4` 是 `STR-2` 的唯一实质补丁。只靠「只监听回环」，本机进程仍然畅通。

## 6. 第 5 步：可观测与容量

| 项 | 目标 | 验收 |
|---|---|---|
| traceId | 一次提交在 question / judge / 沙箱三处日志可串起来 | 按 traceId `grep` 能得到完整的「提交 → 判题 → 落定」时间线 |
| `CON-5` DLQ 重放 | 管理台之外提供一条命令/接口，把死信按 id 重新投递 | 人为造一条死信，执行重放后提交最终落到终态 |
| 压测 | 知道队列堆积与消费速率 | 固定 50 并发提交，记录 P95 判题耗时、队列峰值、是否触发 DLQ |
| `CON-4` 本地消息表 | 落库与发消息最终一致 | 停掉 MQ 后提交，恢复后 30 秒内自动补发并判题完成 |

## 7. 第 6 步：结构性改造

按「改动成本从低到高」排，且每一项都应先有明确理由再动：

1. **`ENV-4` 多机部署**：改 `server.address`、`nacos.discovery.ip`、安全组。属于配置层，但会推翻「inner 不可达」的现有假设，必须与 `SEC-4` 一起做。
2. **`SEC-5` 网关鉴权**：见 §5。
3. **`STR-1` 分库**：先按服务拆 schema（仍可同实例），再考虑物理分库。拆之前要先解决跨服务 join 的替代方案（当前靠 Feign 补全用户信息）。

## 8. 已否决与延后

这一节记录**已经讨论过、当前不做**的方向，以及重新评估的条件。

| 方向 | 相关 ID | 当前结论 | 触发条件 |
|---|---|---|---|
| C++/Go 沙箱 | `JUD-1` | 不做。前端选项已删；枚举值保留给将来扩展 | 确有用户需求，且愿意承担镜像体积、编译工具链、每种语言的资源画像与安全策略 |
| 容器内存上限随题目动态下发 | `JUD-4` | 延后。优先用固定高上限兜底（见 §3.1 方案 A） | 需要按题目精细控制资源时再改协议 |

| Sentinel 端口迁移 | `STR-3` | 等 dashboard 落到本地再做。改动点已确认：user / question / judge 三个 `application.yml` 的 `spring.cloud.sentinel.transport.dashboard`（当前 `localhost:8080`）；网关 yml 没有 sentinel 配置块 | 用户把 sentinel-dashboard 拉到本地 |
| Sentinel 限流规则 | — | 不做。依赖已引入但未配规则，先有压测数据再定阈值 | 完成 §6 压测 |
| 比赛 / 排名 / 系统设置页面 | `FEAT-2` | 保持占位页。三个页面都不影响主链路 | 判题闭环与数据可信度稳定之后 |
| Nacos 配置中心 | — | 不做。当前配置量小，`application.yml` 够用 | 出现「多环境同一配置要改多处」的痛点时 |
| 微信登录 / 帖子 / 点赞收藏 | — | 不做。属于模板残留，与 OJ 主链路无关 | 不考虑 |
| 沙箱联调流程固化（VM 重建 jar、RabbitMQ 隧道） | `ENV-2`、`ENV-3` | 暂不写成脚本。当前只有一个人在部署，脚本成本高于收益 | 出现第二次「旧 jar / 隧道没通」的排障时间损失时 |

## 9. 怎么判断这一轮做完了

不是「代码合并了」，而是下面三条同时成立：

1. 一个没参与过这个项目的人，只读 `docs/` 就能在本地跑起来并完成一次提交判题（依赖 `ENG-1`）。
2. 做题页提交后能看到真实的判题结论，且该结论与用户代码的实际行为一致（依赖 `FEAT-1` + `JUD-4` + `JUD-5`）。
3. 同一条消息重复投递、服务重启、沙箱短暂不可用三种情况下，提交都不会停在中间态（依赖 `CON-1`/`CON-2` 已修 + `CON-4` + `CON-5`）。
